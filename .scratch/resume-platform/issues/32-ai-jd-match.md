# 32 — JD 匹配（`match` 能力）

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：18（结构化内容）、25（章节类型）
- **Blocks**：—
- **ADR**：—

## 背景

市场调研发现 Huntr 的差异化是"**不仅匹配关键词，还匹配职责与资格**"（语义匹配，而非关键词比对）。

国内对应能力：超级简历的 6 项 AI 技能之一即针对 JD 优化。

当前项目**完全没有 JD 相关能力**。

## 任务

### 1. 新增 `match` AI 能力

- 端点 `POST /api/ai/match`（JSON → SSE）
- 输入：简历结构化内容 + **JD 文本**（用户粘贴）
- system prompt 为 Go 常量（`aiMatchSystemPrompt`）

### 2. 匹配层次（分层输出，从确定到语义）

| 层次 | 内容 | 是否需要 AI |
|---|---|---|
| **L1 · 硬性关键词** | JD 中出现的技能/工具词，简历中**有/无** | **不需要 AI**——纯字符串匹配，结果确定 |
| **L2 · 同义词与变体** | `React` ↔ `React.js` ↔ `ReactJS`；`前端` ↔ `Web 前端` | 需要**别名表**（不需 AI） |
| **L3 · 语义匹配** | "负责前端架构" ↔ "需要 3 年 React 经验" | **需要 AI** |
| **L4 · 缺口建议** | 缺什么、怎么补（措辞而非造假） | 需要 AI |

**L1/L2 必须本地实现**——它们是确定性的、免费的、可解释的。**不要把所有事都交给 AI。**

### 3. 与章节类型配合（工单 25）

- "需要 3 年工作经验" 的匹配**必须知道哪些是工作经历**——这是工单 25 的必要性
- 实习经历是否计入工作年限：**默认不计入，但明确标注**

### 4. 输出形态

- **命中/缺失清单可溯源到 JD 与简历的具体位置**
- **不输出"匹配度 87%"这类单一分数**（沿用 ADR-0005 的边界）
- 缺口建议**必须是"如何更好地表述已有经历"**，不是"建议编造经历"

### 5. 前端

- JD 粘贴区
- 并排高亮：JD 中的关键词 ↔ 简历中命中/缺失
- 结果可"一键应用到简历"（走工单 34 的提案机制）

## 验收标准

- [ ] L1 关键词匹配**本地实现**，不消耗 AI 调用
- [ ] L2 别名表可扩展（`React` / `ReactJS` / `React.js` 等）
- [ ] L3 语义匹配由 AI 完成
- [ ] **输出无单一匹配分数**
- [ ] 命中/缺失可溯源到具体位置
- [ ] 缺口建议不鼓励编造经历
- [ ] 游客被拒绝；无 AI 权限时中文错误
- [ ] 后端测试覆盖 L1 与 L2（无需真实 AI 调用）

## 备注

- 💡 **L1/L2 本地实现是成本控制的关键**——如果每次都调 AI 做字符串匹配，成本会失控且结果不如正则确定。
- ⚠️ **不要把"匹配度"做成 KPI 式指标**。用户的真实目标是"这份简历能不能通过这个岗位的筛选"，不是"拿到一个高分"。
- 与工单 31 的关系：31 是"通用内容质量"，32 是"针对特定 JD 的匹配"。**两者不同，不要合并。**
