# 31 — AI 诊断（`analyze` 能力）

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：18（结构化内容）、25（章节类型）
- **Blocks**：—
- **ADR**：[ADR-0005](../../../docs/adr/0005-ats-report-is-fact-only.md)

## 背景

后端**只有两个 AI 能力**：`parse`（文本 → 简历）与 `chat`（对话式改写）。**无 analyze / score / match / optimize。**

同时 ADR-0005 严格分离了两件事：

| | 衡量什么 | 性质 |
|---|---|---|
| **解析可读性**（工单 07 的 ATS 体检） | 文件能否被机器读取 | **事实，不可辩驳** |
| **内容质量**（本工单） | 简历写得好不好 | **主观，需 AI 判断** |

**本工单做后者，且必须与前者保持分离。**

## 任务

### 1. 新增 `analyze` AI 能力

- 新增端点 `POST /api/ai/analyze`（JSON → SSE 流式，沿用 `chat` 的形态）
- **system prompt 作为 Go 常量**（沿用 `aiParseSystemPrompt` / `aiChatSystemPrompt` 的既有模式），新增 `aiAnalyzeSystemPrompt`
- **temperature 建议 0.2**（诊断需要稳定，不要创意）

### 2. 诊断维度（建议，需在 prompt 中明确）

| 维度 | 检查什么 |
|---|---|
| 量化程度 | 经历是否含具体数字（"提升 30%" vs "显著提升"） |
| 动词强度 | 是否用行动动词而非"负责/参与" |
| 与 JD 的相关性 | 仅在有 JD 时（工单 32） |
| 冗余与空话 | 套话、无信息量表述 |
| 完整性 | 是否缺关键章节（应届生缺项目经历等） |
| 一致性 | 时间断层、格式不一致 |

### 3. 输出形态（硬要求）

- **每条建议必须可溯源到具体位置**（哪个章节、哪个条目）
- **每条建议可单独接受/拒绝**——与工单 34 的提案机制配合
- **不输出单一总分**（ADR-0005 的边界同样适用于内容质量：一个无法逐行辩护的分数不该发布）

### 4. 配额

- 本工单**只做能力**，用量记账见工单 33
- 门禁沿用现有 `permission_grants` 的 `ai:use_global`
- 游客账户**不可调用**（沿用现有的 `GUEST_READONLY` 拒绝）

### 5. 已知限制的处理

⚠️ 后端 chat 的 system prompt 要求**每轮重发整份 Markdown 文档**。诊断同样需要全文。

若简历很长：**工单 10 的截断修复必须已完成**，否则中文简历会被静默切成 6,600 字，诊断结果无意义。

## 验收标准

- [ ] `POST /api/ai/analyze` 可用，SSE 流式返回
- [ ] 输出中每条建议**带明确位置引用**
- [ ] **输出中没有单一总分**
- [ ] prompt 为 Go 常量，可被测试覆盖
- [ ] 游客账户被拒绝
- [ ] 无全局 AI 权限时被拒绝，错误为中文
- [ ] 有测试覆盖 prompt 结构与权限
- [ ] 长中文简历（> 20,000 字节）不被截断

## 备注

- ⚠️ **不要与 ATS 体检混在同一个界面**。用户需要理解："这个文件机器读得到吗"（事实）与"这份简历写得好吗"（意见）是两个问题。
- AI 用量与成本记账见工单 33——**AI 调用是真金白银，必须有可观测性**。
