# 40 — 简历复制与变体管理

## 背景

**后端完全没有任何复制/变体能力**：

- 无 `duplicate` 端点
- 无 `PATCH`
- 无批量操作
- 无重命名
- slug 创建后不可变

**而求职者的真实用法是"一岗一简历"**——同一份底稿，针对不同岗位调整。

当前用户只能手动复制粘贴创建第二份，然后两份各自独立演化，**没有任何关联**。

调研中的产品：多数支持"创建副本"。

## 任务

### 1. 复制

- 新增 `POST /api/resumes/{id}/duplicate`
- 复制内容 + 展示态 + 元数据
- **不复制**：版本历史、访问统计、审批状态（新副本默认为 draft/private）
- 新 slug 由后端生成（工单 13 的修复已保证纯中文名可用）

### 2. 变体关系

```sql
ALTER TABLE resumes ADD COLUMN variant_of uuid;        -- 指向原始简历
ALTER TABLE resumes ADD COLUMN variant_label varchar(64);  -- 如「投字节」「英文版」
```

走工单 11 的迁移器。

### 3. 变体的语义（本工单需要决策）

| 问题 | 建议 |
|---|---|
| 变体是否跟随原稿更新？ | **不跟随**——变体是独立副本，避免"改了原稿，变体被动变化"的意外 |
| 是否可以脱离变体关系？ | 可以（"另存为独立简历"） |
| 变体是否共享版本历史？ | **不共享**——各自独立 |
| 删除原稿时变体？ | **保留**，仅解除 `variant_of` 关联 |

> **理由**：所有"共享/跟随"的语义都会引入"我改了一处，另一处意外变了"的风险。**独立副本 + 弱关联标签**是最可预测的模型。

### 4. 中文特有：内推/定向投递的常见变体

- 「投字节」「投阿里」这类**公司定向变体**
- 「技术岗」「管理岗」这类**岗位定向变体**
- UI 上支持给变体打标签，并按原稿分组展示

### 5. UI

- 简历列表按变体分组（原稿 + 其变体）
- 复制按钮
- 变体标签编辑
- 从变体创建新变体

## 验收标准

- [ ] 可复制简历，内容/展示态/元数据完整复制
- [ ] 不复制版本历史与访问统计
- [ ] 副本默认为 private/draft（**不得自动公开**）
- [ ] 变体关系可建立、可解除
- [ ] **变体不跟随原稿更新**（验证：改原稿，变体不变）
- [ ] 删除原稿后变体仍可访问
- [ ] 列表按变体分组展示
- [ ] 变体标签可编辑
- [ ] 后端测试覆盖复制与关联逻辑
- [ ] 游客账户不可复制

## 备注

- ⚠️ **审批状态的处理很关键**：副本若继承了 `approved` 状态，会**绕过审核直接公开**。必须默认为 draft。
- 变体数量会有上限需要吗？**建议暂不设限**，但记录该决策。
