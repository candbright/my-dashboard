# 06 — 纯文本 (.txt) 导出

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：01（测试基建）
- **Blocks**：07（ATS 体检界面共用渲染逻辑）
- **ADR**：[ADR-0005](../../../docs/adr/0005-ats-report-is-fact-only.md)

## 背景

市场调研发现一个**反直觉的事实**：头部产品把"ATS 安全的格式"设为**免费的那一档**——

- Resume.io 免费层**只给 TXT**（"Downloads only in TXT format"）
- Zety 免费仅 TXT
- MyPerfectResume 免费仅 `.txt`

逻辑是：**纯文本不值钱，设计才值钱。**

而国内**没有任何产品把纯文本导出做成一等功能**。

成本：从结构化内容生成纯文本，**约 40 行**。

## 任务

1. 新增 `src/lib/resume-text.ts`：
   ```
   resumeToPlainText(content: StructuredContent): string
   ```
2. 输出格式（**为 ATS 优化，不为好看**）：
   - 姓名、职位、联系方式逐行，**不加装饰字符**
   - 章节标题用纯文本行 + 空行分隔
   - 条目：公司/职位/日期同行，要点用 `-` 前缀
   - **不使用** `│`、`═`、`▪` 等装饰符号（解析器可能误读）
   - **不使用**多栏模拟（不用空格对齐制造列）
3. 编码：**UTF-8**（中文必需），文件名建议 `{姓名}-{职位}.txt`
4. 在导出菜单中提供，与 PDF 并列
5. 测试：给定结构化内容 → 输出**以 UTF-8 解码后中文字符数正确**、无控制字符、无装饰符号

## 验收标准

- [ ] 导出的 `.txt` 在记事本/VS Code 中中文无乱码
- [ ] 无 `│`/`═`/`▪` 之类装饰字符
- [ ] 无"用空格模拟双栏"的排版
- [ ] 中文字符数与原内容一致
- [ ] 有测试覆盖
- [ ] **与工单 07 共用同一纹理渲染逻辑**（不要在 07 里再写一份）

## 备注

- 这是**成本最低、信号最高**的差异化项之一。
- 💡 产品化建议：把「`.txt` 导出」+「解析器视角预览」（工单 07）打包成一个叫 **「ATS 体检」** 的功能。两者都不需要新的 AI 调用，却直接对标国内头部在宣传的 "ATS 系统兼容性校准"。

### ⚠️ 工单的签名与工单集自相矛盾，已按可行方式落地

工单第 27 行要求 `resumeToPlainText(content: StructuredContent)`，但 **`StructuredContent` 要到工单 18 才存在**（P2 结构化内容阶段），而本工单的 `Blocked by` 只写了 01。这是工单集内部的不一致，不是我的实现选择。

采用的做法：**输入类型按结构声明**（`PlainTextSource` = `{ frontmatter?, sections? }`），而不是从 `@/lib/resume-parser` 导入 `ParsedResume`。

这样做的好处是工单 18 落地时**本模块不需要改一行**：只要服务端的 `StructuredContent` 也有 `frontmatter` 与 `sections` 字段，结构上就自动满足；即使字段名有出入，改动也只落在这一个类型声明上，**渲染逻辑（这些行数、规则）一行都不用动**。这正好把"约 40 行成本"那句话的意思落实了——值钱的是这些规则，不是容器类型。

字段类型声明为 `unknown` 而非 `string`，原因见下面的缺陷 1。

### ATS 优化 = 一连串**克制**，每条都对应一种常见错误

工单只列了"不加装饰字符""不用空格模拟双栏"两条。实现时补全了同类规则，因为它们都是解析器会**误读**的东西：

| 规则 | 不这样做的后果 |
|---|---|
| 无 `│ ═ ▪ • ◆ ·` 等装饰符 | 被当作内容读入；`·` 是视觉展示页用的分隔符，导出里出现就是工单禁止的"装饰" |
| 无多空格对齐、无制表符 | 制表符与连续空格正是伪造双栏的材料；制表符在不同解码下宽度还不同 |
| 无 Markdown 残留 | `**负责**` 在 TXT 里不是粗体，是要么被解析器剥离、要么**原样进入字段**的噪声 |
| 表格边框拆除 | Markdown 表格在纯文本里**就是**工单禁止的列布局 → 删分隔行、把 `\|` 变空格，但**保留单元格文字**（项目表格的内容是真实简历内容） |
| 联系方式一项一行 | 一行里同时出现邮箱与电话，会让按模式提取的解析器抓到一个跨越两者的区间 |
| 标题与正文之间空行 | 让"标题→内容"的归属无歧义 |
| 区域性 CRLF/CR 归一 | 行级 Markdown 规则锚定 `$`，多一个 `\r` 会让 `$` 匹配失败，**静默关闭整组行级规则** |
| 不折行、不对齐、不居中 | 这个文件是给机器读的，其次才是给人用等宽编辑器看 |

**有意不做**：把 `section.content` 按"技能"之类的关键词跳过。视觉展示页（`ResumeDisplay`）对技能类章节改用标签网格渲染，所以那些正文不显示；但纯文本导出的目标是**不丢内容**，因此这里照常输出。

### 过程中抓到两个真实缺陷

**1. 未加引号的电话号码让整份导出崩溃。**
真实 YAML `phone: 13800138000` 被解析成 **number**，而不是 string。我最初直接对它调用 `.replace()`，抛 `value.replace is not a function`，**整份导出失败**——而这正是最自然的写法（没人给电话加引号）。`ResumeRecord.phone` 声明为 `string | null` 只是对 API 的镜像，**运行时并不受约束**。

修法：加一个 `asText(value: unknown)` 边界函数，把所有 frontmatter 值先强制成字符串，并把输入类型如实声明为 `unknown`。回归测试用**真实解析器**跑未加引号的电话。

**2. Markdown 表格的分隔行 `| --- | --- |` 会残留。**
它不在"整行仅由 `-` 构成"的形态上，所以主题分隔线规则抓不到；结果导出的 TXT 里有 `---`，既是工单禁止的装饰，也是我自己的验收断言（不得含 `---`）会漏掉的东西。修法：表格先行处理（删分隔行、把行内 `|` 变空格），再走其余规则。

两个缺陷都是**先跑起来才发现的**——类型检查全绿。

### 验收

| 验收标准 | 结果 |
|---|---|
| 导出的 `.txt` 在记事本/VS Code 中中文无乱码 | ✅ MIME 为 `text/plain;charset=utf-8`、**不写 BOM**、CJK 落盘为多字节 UTF-8 序列；断言 encode→decode 往返一致、`\ufffd` 不出现 |
| 无 `│`/`═`/`▪` 之类装饰字符 | ✅ 断言 15 种装饰符不出现，**包括作者手打进正文的**（会被移除，而非放行） |
| 无"用空格模拟双栏"的排版 | ✅ 断言全文不含连续 2 个及以上空格、不含制表符 |
| 中文字符数与原内容一致 | ✅ 严格相等断言（同时抓丢失与新增），并断言要点原文完整出现 |
| 有测试覆盖 | ✅ 58 个测试 |
| **与工单 07 共用同一纹理渲染逻辑** | ✅ `markdownToPlainText` 与 `resumeToPlainText` 均导出；工单 07 的预览应直接调用 `resumeToPlainText`（**不要**另写一份） |

另：无 C0 控制字符（除换行）已断言；全角标点保持原样**不折叠为 ASCII**（`（高并发），` 不会变成 `(高并发),`）——整串 NFKC 会改掉 ATS 存下的文字，这是工单 03 从另一个方向踩过的同类问题。

### 遗留与已知边界

- **未做真实手动开文件验证**。验收标准写的是"在记事本/VS Code 中无乱码"，这需要人在 Windows 上打开文件。已用可自动化的等价手段覆盖（charset、无 BOM、UTF-8 往返、多字节断言），但**像素级/编辑器级确认未做**。
- **零宽空格（ZWSP）会原样通过**。它不是 C0 控制字符，剥离它意味着做 Unicode 类别归一，超出本工单范围；对 ATS 无害（不可见、不切断词）。已用断言把这个行为**固定下来**，避免无人察觉地变化。
- **有序列表保留序号、无序列表去掉标记**（`1. 第一项` 保留，`- 无序项` → `无序项`），因为序号携带解析器可能使用的语义，而 `-` 不携带。
- 权限上复用了 `can_view_source`：纯文本导出的内容与"源码视图"可见的内容是同一份。后端 `can_export_pdf` 目前被硬编码为 `true`（见工单 14），本工单未新增独立权限位。
- 与工单 07 的 `Blocks` 关系已就绪：`resumeToPlainText` 就是"解析器视角预览"要显示的文本。
