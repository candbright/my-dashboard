# 26 — 中文特有字段 + 自定义字段

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：17（元数据迁入列）、15（元数据编辑面板）
- **Blocks**：27、32
- **ADR**：[ADR-0003](../../../docs/adr/0003-structured-content-model.md)

## 背景

国内市场调研列出的中文特有字段，当前项目**一个都没有**：

| 字段 | 为什么必需 |
|---|---|
| **政治面貌** | 国企、事业单位、公务员岗的必填项（中共党员/共青团员/群众/民主党派） |
| **籍贯** | 常见要求，格式为 **省 → 市 → 旗县**（注意内蒙等地的"旗县"层级） |
| **民族** | 部分岗位要求 |
| **出生年月** | 比"年龄"更常见（年龄会过期） |
| **婚姻状况** | 社招常见 |
| **期望薪资** | 国内简历标配（如 `15-20K·14薪`） |
| **期望城市 / 求职意向** | 校招与社招都常见 |
| **下属人数** | 管理岗简历特有 |
| **离职原因** | 部分国内模板要求 |
| **身高/体重** | 少数岗位（如空乘、部分服务业） |

同时国内产品（简历本）的解法是提供**自定义字段**——用户可自行添加任意字段。

## 任务

### 1. 新增元数据列（走工单 11 的迁移器）

⚠️ **加列需改四处**：`ResumeModel` / 领域结构体 / `toResumeDomain` / `toResumeModel`

将字段分为三组，避免 `resumes` 表列数失控：

- **A. 高频且需查询的**（进 `resumes` 主表列）：`political_status`、`native_place`、`ethnicity`、`birth_date`、`marital_status`
- **B. 低频的**（进 `resumes` 主表列即可，无需索引）：`expected_salary`、`expected_city`、`job_intention`、`subordinate_count`、`resignation_reason`
- **C. 用户自定义的**（进 `resumes.custom_fields` JSONB）：任意 `{label, value}` 数组

### 2. 籍贯的层级结构

`native_place` 需要 省 → 市 → 旗县 三级。方案：
- 简单：单个文本字段
- 结构化：JSONB `{province, city, district}`

**建议单文本字段**——结构化需要完整的行政区划数据（数千条目），收益不足以支撑。

### 3. 自定义字段

- `resumes.custom_fields` JSONB：`[{ label: "身高", value: "175cm" }]`
- 服务端校验（沿用工单 19 的校验模式）：label 非空、长度限制、数量上限（如 20）
- UI 上可增删、排序、显示/隐藏

### 4. UI 集成

纳入工单 15 的元数据面板，**分组展示**（基本信息 / 求职意向 / 其他 / 自定义），避免一次铺开 15 个字段造成压迫感。

### 5. 展示与导出

- 公开页（`ResumeDisplay`）与 PDF 中按国内惯例排列
- **空字段不显示**（不要出现"政治面貌：—"）

## 验收标准

- [ ] 三组字段全部可编辑并持久化
- [ ] 自定义字段可增删、排序、上限生效
- [ ] 空字段在展示页与 PDF 中不占位
- [ ] 籍贯等中文值在数据库与导出中无乱码
- [ ] 服务端校验：非法值、超长、超数量被拒绝并返回中文错误
- [ ] 工单 17 的"保存正文不覆盖元数据"对这些新字段同样成立
- [ ] 后端测试覆盖新列的读写

## 备注

- ⚠️ `resumes` 表列数会显著增长。若将来字段继续增加，**考虑抽出 `resume_profiles` 表**——但当前不建议（ADR-0003 已让表变宽，再拆表会让迁移复杂化）。
- 这些字段**不参与 ATS 解析可读性**判定——它们是内容，不是格式。
