# 25 — 项目经历 / 工作经历自动区分

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：18（服务端解析器权威）
- **Blocks**：32（JD 匹配依赖此语义）
- **ADR**：[ADR-0003](../../../docs/adr/0003-structured-content-model.md)

## 背景

国内市场调研的技术基准（100分简历宣称）：**98% 准确率、20 秒内完成**简历解析与「项目经历 vs 工作经历」自动归类。

**这是应届生"能用/不能用"的分界线**——应届生的简历主体是项目经历，而通用解析器常把两者混为一谈。

当前项目**没有任何分类逻辑**——章节只是按标题字符串匹配（`title.includes('技能')` 之类）。

## 任务

1. **在结构化快照中标注章节类型**（工单 18 的延伸）：
   ```
   type SectionType = 'summary' | 'work' | 'project' | 'education' | 'skills' | 'certificate' | 'award' | 'custom'
   ```
2. **分类策略（分层，从确定到启发）**：
   - **第一层 · 显式标题**：`工作经历`/`工作经验`/`实习经历` → `work`；`项目经历`/`项目经验`/`作品` → `project`；`教育背景`/`教育经历` → `education`
   - **第二层 · 条目内容特征**：
     - 有「公司名 + 职位 + 起止时间」→ `work`
     - 有「项目名 + 角色 + 技术栈/职责」→ `project`
     - 有「学校 + 专业 + 学历 + 时间」→ `education`
   - **第三层 · 交叉校验**：同一条目里出现公司名又出现技术栈时，以标题层为准并记录不确定标记
3. **不确定时必须可标注**：快照中带 `confidence: 'high' | 'low'`，**低置信度的分类在 UI 上可被用户一键纠正**
4. **用户纠正后要能被记住**——纠正结果写入章节类型（存于文档的章节标注或展示态），**不要每次重新猜**
5. **应届生场景特殊处理**：教育背景应排在项目/工作经历**之前**（国内应届生惯例）；这条顺序规则可由展示态覆盖

## 验收标准

- [ ] 快照中每个章节都有 `type` 与 `confidence`
- [ ] 三组测试样本（应届生 / 社招 / 转行）分类正确
  - 应届生：教育背景 + 2 个项目经历，无工作经历
  - 社招：2 段工作经历 + 1 个项目经历
  - 标签缺失/混合：必须给出 `low` 置信度而非猜错
- [ ] 低置信度分类在 UI 上可一键纠正
- [ ] 用户纠正后不再重复误判
- [ ] 应届生的章节默认顺序正确（教育在前）
- [ ] 后端有表驱动测试覆盖三层策略

## 备注

- ⚠️ 不要用 AI 做这个分类——它是**确定性问题**，规则能做得更好、更快、可解释、零成本。AI 可作为低置信度时的兜底，但**不是第一手段**。
- 这个分类是工单 32（JD 匹配）的语义基础：匹配"需要 3 年工作经验"时必须知道哪些是工作经历。
