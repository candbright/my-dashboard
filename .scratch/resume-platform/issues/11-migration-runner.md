# 11 — 版本化迁移器 + `schema_migrations`

- **Type**：task
- **Status**：ready-for-agent
- **Blocked by**：无
- **Blocks**：12、16、19、26、30、35、36、38
- **ADR**：[ADR-0006](../../../docs/adr/0006-versioned-migrations.md)

## 背景

Schema 变更完全依赖 GORM `AutoMigrate`（`internal/data/*/Migrate()` 里的 `db.AutoMigrate(...)`）。**无 SQL 文件、无版本历史、无回滚。**

三个硬局限（详见 ADR-0006）：

1. **不会创建 GIN / 表达式索引**——即将需要的 `resumes(visibility, approval_status)` 复合索引、`pg_trgm` 搜索索引都做不到
2. **对非空表新增 `NOT NULL` 无默认值的列会直接让服务启动失败**（发 `ALTER TABLE … NOT NULL` 但不回填）
3. **无记账**——无法知道当前库在哪一版

即将发生的变更包括四张表级别的改动与一次破坏性数据迁移。`AutoMigrate` 承载不了。

## 任务

1. 新增 `schema_migrations` 表：`(version, name, applied_at, checksum)`
2. 实现迁移注册与执行：
   ```go
   var migrations = []Migration{
       {Version: 1, Name: "add_resume_version_column", Up: func(tx *gorm.DB) error { ... }},
   }
   ```
   - **编译进二进制**，无需外部工具
   - 启动时按序执行未应用的迁移
   - 每条在**独立事务**内完成并记账
3. **支持非事务迁移**——`CREATE INDEX CONCURRENTLY` 不能在事务内执行（ADR-0009 明确要求）
4. **`checksum` 校验**：启动时比对已应用迁移的校验和，不匹配则**拒绝启动**（防止偷改历史迁移）
5. **失败语义**：迁移失败 → **拒绝启动**（fail-fast），日志给出**失败编号与原因**
   - 与既有风格一致：`AI_KEY_ENCRYPTION_SECRET` 未设置本来就 `panic`，Postgres 不可达本来也起不来
6. **基线处理**：
   - 全新部署 → `AutoMigrate` 建基线，随后把已有迁移标记为已应用
   - 存量部署 → 从基线版本开始逐条应用
7. **`AutoMigrate` 保留但降级**为"基线建表"角色，不再作为日常变更手段
8. **在 `DEPLOY.md` 写明**：无自动回滚脚本，**回滚靠备份恢复**

## 验收标准

- [ ] 重复启动**不重复执行**（幂等）

### 关键设计决定（留给工单 12+）

1. **基线版本是 0，不是 1。** 真实迁移从 1 开始，这样**版本号与工单号对齐**（工单 12 的迁移就是版本 1）。若基线占 1，此后每一版都错位一位。基线行固定为 `(0, "baseline_automigrate", "automigrate-baseline/v1")`。
2. **"空 `schema_migrations`" 同时表示全新库与存量库**，迁移器**不区分**。判据故意不是"`resumes` 表是否存在"——那会让迁移器耦合到某一个模块的模型上。两条路径的行为差异只在日志措辞，因为 `baselineSchema` 对已存在的表是幂等无操作。
3. **`AutoMigrate` 只在一个地方被调用**：`data.go` 的 `baselineSchema` 回调，且仅在无基线记录时执行一次。
4. **记账写在迁移自己的事务内**（Postgres 有事务性 DDL）。`TestUpWritesTheRecordInsideTheMigrationTransaction` 不是读代码，而是断言 `INSERT` 的**事务深度为 1**——这样"改了"和"记了"不可能不一致。非事务迁移只能分开写，已在文档里注明**非原子**。
5. **`checksum` 覆盖 `version + name + NoTransaction + Shasum`，不覆盖函数体**——Go 无法稳定地哈希闭包的机器码（随编译器版本/构建参数/架构变化），那样会导致"升级 Go 工具链后无人动过的库拒绝启动"，比不校验更糟。这个缺口**明写在 `Migration.checksum` 的文档注释里**；裸 SQL 迁移用 `migrate.ShasumOf(sql)` 填 `Shasum` 即可闭合。
6. **`migrations` 注册表目前是空的**，这是刻意的：工单 11 只交付框架，让工单 12 的**第一条真实迁移**（加列 + 回填 + `NOT NULL` —— 恰好是 `AutoMigrate` 做不到的组合）来端到端验证它，而不是这一单同时做两件事。
7. **`MigrateApprovals` 没有改成迁移**：它是纯 `INSERT` 回填、不是 schema 变更，且已有自己的"只跑一次"标记（与数据同事务写入）。
8. **未实现多副本并发保护（Postgres advisory lock）。** 当前是单实例部署，`CREATE TABLE IF NOT EXISTS` + 仅启动时执行 + `version` 主键已足够。若将来横向扩容，**这是必须先补的**——两个副本同时启动会有一个因主键冲突而启动失败（失败是安全的，但会误报）。

### 顺带修掉的两个真实问题

1. **[`internal/data/resumevault/resume.go`](D:/project-me/kratos-server/internal/data/resumevault/resume.go) 带 UTF-8 BOM，会被提交进仓库。** 工单 09 编辑该文件时引入。BOM 是文件字节的一部分、会被提交，且 `gofmt` 直接拒绝解析。已去除，全仓 `.go` 文件 BOM 计数归零。
2. **新增 [`.gitattributes`](D:/project-me/kratos-server/.gitattributes)**：全库 `text=auto eol=lf` + 二进制保护。理由是 `core.autocrlf=true` 让工作区变 CRLF，而 `gofmt` 写 LF，于是 `gofmt -l` **把每个文件都报成未格式化**——这个检查项因此彻底失效。已在 `AGENTS.md` 写明"Windows 检出下 `gofmt -l` 命中要先排除 CR，但 BOM 是真问题"。（试过用 `*.go -text` 让 gofmt 检查变干净，但 `git check-attr` 证明全局 `core.autocrlf=true` 会盖过它，所以没有采用那种误导性写法。）

同时更新了 [`kratos-server/AGENTS.md`](D:/project-me/kratos-server/AGENTS.md)：新增 Database 小节（迁移规范）、`data/migrate` 的文件表项、以及 Development Notes 里"仓库内 `configs/config.yaml` 是陈旧的（dbname `infra` 不存在、缺 `ai.key_encryption_secret`）"和"`go build ./...` 的 `a.out.exe` 文件占用不是编译错误"两条踩坑记录。原文"Database auto-migrates on startup — no separate migration step needed"已过时，一并改写。
