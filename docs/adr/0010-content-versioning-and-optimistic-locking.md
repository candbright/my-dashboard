# ADR-0010：内容版本与乐观锁

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0003（内容模型）、ADR-0004（展示态）、ADR-0006（迁移）

## 背景

`resumes` 表**没有 `version` / `etag` 列**，`PUT /api/resumes/{id}` 是**后写覆盖**。

同时计划引入**自动保存**——而自动保存是行业门槛功能（当前只能手动保存）。

### 这两件事有硬依赖

自动保存会让保存请求变得**频繁且并发**：

- 两个标签页同时打开同一份简历 → 交替覆盖
- 自动保存请求与用户主动保存竞争
- 网络重试导致同一内容被重复提交

**在没有并发控制的表上开启自动保存，等于主动制造数据丢失。**

### 另一个并发的真实缺陷

后端 `generateSlug` 的唯一性检查是**先查后插、无重试**：

```go
exists, _ := uc.resumeRepo.SlugExists(ctx, slug)
if exists { slug = slug + "-" + id[:8] }
```

两个请求同时查到"不存在"，然后一起插入——其中一个撞唯一约束，表面为 **500**。

## 决策

### 1. 新增 `version` 整数列 + 乐观锁

- 每个简历一行一个 `version` 整数。
- 保存请求**必须携带读取时的版本**。
- 版本不匹配 → **HTTP 409 Conflict**，附当前版本与最后修改时间。
- **`version` 与展示态共用**（ADR-0004）——内容更新与样式更新互相不能覆盖。

### 2. 冲突处理：提示 + 保留较新版本

**不做自动三方合并。** 冲突时前端提示用户，并明确告知"服务端有更新版本"，让用户选择。

理由：在 Markdown 上做三方合并，**正确性风险远高于收益**。合并算法一旦有 bug，会静默产生用户从未写过的内容——这是最不该出错的地方。

### 3. 每次保存写一条内容快照

新增 `resume_versions` 表，每次保存追加一条**完整 Markdown 快照**。

**为什么是完整快照而不是 diff**：快照在 Markdown 上**零正确性风险**。diff（JSON Patch）省空间，但重建一旦有 bug，**回滚会静默损坏内容**。

**这一步同时买到两样东西**：
1. 数据安全网（自动保存出错可回滚）
2. 报告列为差异化功能的「真正的版本历史」——竞品简历本有撤销但**保存退出即清空**，无人做好

### 4. 快照的约束

| 约束 | 值 | 理由 |
|---|---|---|
| **不含展示态** | 只快照简历文档 | 否则"换个颜色"污染内容历史，回滚语义模糊（ADR-0004） |
| **上限** | **配置项**，默认 50 条/简历 | 存储是磁盘文件，且是**全项目唯一无服务端大小限制的字段**。硬编码会让自托管用户无法按磁盘情况调整 |
| **可见性** | 跟随简历现有规则（owner / admin） | 不新增权限类型（ADR-0009） |
| **不自动合并** | 见上 | |

### 5. 顺带修复 slug 竞态

**让数据库唯一约束来保证，并捕获冲突后重试**，而不是先查后插。

## 后果

**正面**
- 自动保存不再制造数据丢失。
- 版本历史（差异化功能）几乎免费获得。
- 展示态与内容的一致性由同一个 `version` 保证。
- slug 竞态的 500 被消除。

**负面 / 代价**
- **`version` 列需要回填**——必须走 ADR-0006 的迁移器（`AutoMigrate` 无法对非空表加 `NOT NULL` 无默认值的列）。这是**第一条迁移**，用它验证迁移器的端到端流程。
- `resume_versions` 表随使用增长；依赖配置项上限约束。**须有清理逻辑**，否则"无人清理的目录"问题会从磁盘转移到数据库。
- `PUT` 的契约变更属**破坏性 API 变更**——前端必须同步改造，旧客户端会被 409 拒绝。需在 `DEPLOY.md` 中说明。
- 冲突时用户需要手动决策，体验不如自动合并流畅。**这是刻意接受的代价。**

**受影响的既有代码**
- `kratos-server/internal/data/resumevault/model.go` + 领域结构体 + 两个转换器（**加列需改四处**）
- `kratos-server/internal/biz/resumevault/resume.go`（`generateSlug` 竞态、`UpdateResumeContent`）
- `api/resumevault/v1/resume.proto`（`UpdateResumeRequest` 增字段）
- `src/lib/api-client.ts`、`src/components/ResumeEditor.tsx`、`ResumePageClient.tsx`

## 实施记录（工单 12 / 16，2026-10-13）

本 ADR 的两半分别由工单 12（乐观锁）与工单 16（内容快照）落地。约束层面无一处被推翻，但有**一处决策在本 ADR 里没有写清、实施时被真实数据库证伪**，记在这里。

### 「单条派生集合 DELETE」不足以强制上限

本 ADR 只说"**须有清理逻辑**"，没说怎么写。工单 16 的第一版实现选了：

```sql
DELETE FROM resume_versions
WHERE resume_id = $1
  AND id NOT IN (SELECT id FROM resume_versions WHERE resume_id = $1
                 ORDER BY version DESC LIMIT $2)
```

理由看似充分：count-then-delete 会互相竞态（两个事务都读到"超了 2 条"，各自删 2 条，共删 4 条），而把"要保留的集合"派生在同一条语句里就没有读-改-写。

**这个推理是错的。** 真实 Postgres 测试（12 并发写入、`keep=5`）留下 **12 行**。

原因是 `READ COMMITTED` 的可见性：子查询只能看到本事务开始前已提交的行，加上自己刚插入的那条。看不到其他在途事务的行。于是 N 个并发保存各自都认为"最新 5 条里只有自己"，全部判定无需删除。

**原子性不等于串行化**——这是本 ADR 应当明确、而当时没有明确的一点。任何"读一个派生集合再据此写"的语句，只要它的读看不到并发写，就仍然需要显式串行化。

**修法**：`Append` 的事务开头取 `pg_advisory_xact_lock(hashtext(resume_id))`，按简历串行化整个"插入 + 裁剪"。不同简历互不阻塞；同一简历本来就被乐观锁按更粗粒度串行化，因此没有牺牲真实存在的并发。`xact` 作用域保证崩溃或断连时自动释放。

### 另外两处实施时的具体化

- **裁剪按 `version DESC` 排序**，而非 `created_at DESC`。自动保存按时钟触发，同秒保存是常态；时间戳打平时 Postgres 会任意挑一条，可能删掉刚写入的那条。`version` 每简历唯一且单调，是无歧义的全序。
- **快照失败不使保存失败**。正文已提交、`version` 已前进，此时报错等于告诉客户端"编辑被拒绝"，而它其实已经存了。历史是安全网，可以降级；保存不可以。失败只记日志。

### 未改动 ADR 结论的部分

- 完整快照、不用 diff —— 已实施。
- 快照不含展示态 —— 已实施（`ResumeVersion` 上**根本没有**展示态字段，用测试断言其字段集合）。
- 上限是配置项、默认 50 —— 已实施为 `resume.history_limit`；`<= 0` 归一到默认值，因为让"未配置"与"保留 0 条"等价会让忘记写配置行的部署静默丢掉整个功能。
- 可见性跟随 owner/admin、**不新增权限类型** —— 已实施（handler 复用编辑路径的判据与错误码）。
- 回滚是"一次追加的保存" —— 已实施，且回滚走的是同一条乐观锁写入，因此会像普通保存一样产生 409，而不是悄悄覆盖。
