# ADR-0002：CJK 渲染预注册 Spike 协议

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0001（渲染引擎选型）

## 背景

ADR-0001 的引擎选择悬在一个**无法从文档回答**的问题上：**Forme 产出的中文 PDF，文字能否被正确提取？**

已核实的事实与其缺口：

- Forme 的输出**确实有文字层**——三条独立证据：redaction 功能移除的是内容流里的 `Tj`/`TJ` 操作符；PDF/UA-1 在 CI 中被 veraPDF 验证通过；`pdfjs-dist` 是它的 devDependency（用 PDF.js 测试自己的输出）。
- **但** Forme 的 redaction 文档明确写着 *"Only WinAnsi encoding… CJK, Arabic, and other non-WinAnsi encoded text cannot be found by text search"*。

这说明 Forme 用 CID/Identity-H 编码写中文，而**它是否输出正确的 `/ToUnicode` CMap，全部文档中均无记载**。

如果中文提取不出来，**Forme 对本项目的核心目标（ATS 可读）价值为零**——那么"有文字层"这件事毫无意义。

同理，它的 CJK 序列化性能修复（issue #182，0.28.0，修复距今数日，数字为厂商自报）也需要实测。

**"能不能提取"是一个只有实验能回答的问题。** 因此把这个实验**预注册**下来：在跑之前写死判据，避免事后为已有的偏好找理由。

## 决策

在写任何渲染相关代码之前，先执行一次**限时 1–2 天的 Spike**。判据如下，**先定判据，后跑实验**。

### 环境

```
@formepdf/core@0.28.0  @formepdf/next@0.28.0  @formepdf/html@0.28.0
```
**必须精确锁版本**——0.1.0 → 0.28.0 只用了 8 个月，且已有过一次破坏性迁移（0.9.0 迁移指南）。

### 测试材料

一份**真实中文简历**，而非合成样本。硬性要求：

- 3–5 页
- ≥ 2,000 个不同汉字
- 含中英混排（技能行的 `React / Vue` 与中文并列）
- 含标点：`，。、；：（）` 与英文逗号混用
- 含数字与日期：`2022.03 - 2024.06`

### 必测项（任一 FAIL 即判定 Spike 失败）

| # | 判据 | 方法 | 通过标准 |
|---|---|---|---|
| 1 | **中文可提取** | `pdftotext` 或 `pdfjs-dist` `getTextContent()` | 抽出的中文**逐字正确**，无 `�`、无 `?`、无缺字 |
| 2 | **`/ToUnicode` 有效** | Chrome 与 Acrobat 中各**搜索一个中文词** | 能搜到并高亮 |
| 3 | **复制粘贴正确** | Chrome 中全选复制，粘进编辑器 | 中文无乱码，段落顺序正确 |
| 4 | **渲染耗时** | 计时上述文档的完整渲染 | **P95 < 1,500 ms**（不设"和英文一样快"，只排除秒级） |
| 5 | **峰值内存** | 记录 Node 进程 RSS 峰值 | **< 512 MB** |
| 6 | **输出体积** | 记录 PDF 字节数 | **< 1.5 MB**（验证子集化真的生效） |
| 7 | **warnings 可接受** | 收集 `renderHtml()` 返回的 `warnings[]` | **逐条读懂并判定可接受**；出现"文字被丢弃"类告警即 FAIL |
| 8 | **构建通过** | Next 16.2.6 + Turbopack 编译 WASM import | 无需额外的 webpack 配置 |

### 补充测试（信息性，不作为判据）

- 页面断点是否与 Chrome 打印一致
- `break-inside: avoid` 在条目级是否生效
- 页眉重复与 `counter(page)` 是否工作
- CJK 序列化耗时实测值（对照 issue #182 声称的 85 ms）

### 判定与后续

```
全部通过  → Forme 为终态引擎（ADR-0001 分支一）
任一 FAIL → headless Chromium 为终态引擎（ADR-0001 分支二）
```

**无论哪个结果，都要把这次的测试文档固化为常驻回归用例**，使"中文可提取"成为被持续验证的性质，而不是一次性结论。

## 后果

**正面**
- 用 1–2 天的成本，消除整个渲染路线最大的不确定性。
- 判据先于实验写定，结论不可事后粉饰。
- 即使 Spike 失败也有明确兜底，不是死路。

**负面 / 代价**
- 阶段四的关键路径前移了 1–2 天。
- Spike 若选 Forme，则接受了一个 pre-1.0、**单维护者**（bus factor = 1）的依赖，必须精确锁版本。
- Spike 结果依赖当时的版本；0.28.0 的 CJK 修复本身只有数日历史，长期稳定性未知。

## 备注：为何不直接选 Chromium

Chromium **几乎肯定能通过第 1–3 项**（CJK 由系统字体栈与 HarfBuzz 保证），而 Forme 通过与否未知。直接选 Chromium 是更稳的路径。

之所以仍先跑 Spike，是因为 Forme 若通过，收益是**一套模板两处跑 + PDF/UA-1 + 零外部容器**——这消除了 ADR-0007 里相当一部分复杂度。**用 1–2 天换取"可能显著简化架构"，且失败也有兜底**，这个交换是划算的。

**若 Spike 结果暧昧不清（如中文可提取但偶发缺字），选择 Chromium。** 一个中文简历产品不能把正确性建立在"大多数情况下可以"之上。

## Spike 结果（2026-10-13 执行）

**判定：判据 5 失败 → 终态引擎为 headless Chromium（ADR-0001 分支二）。**

执行环境：Node v24.13.1；`@formepdf/{core,html,next}@0.28.0` 精确锁版本；字体 `simhei.ttf`；测试材料为本仓库常驻 fixture `.scratch/resume-platform/fixtures/`（11 页，16,605 汉字，**2,271 个不同汉字**，含中英混排、`，。、；：（）` 与英文逗号、`2022.03 - 2024.06` 格式日期）。

| # | 判据 | 实测 | 判定 |
|---|---|---|---|
| 1 | 中文可提取 | 11 页逐字正确；`�` 0 处；无缺字 | **PASS** |
| 2 | `/ToUnicode` 有效 | 输出含 `/ToUnicode` + `/Identity-H` + `/CIDFontType2` + `/FontFile2`（交互搜索未做） | 未验证 |
| 3 | 复制粘贴正确 | 未做（交互） | 未验证 |
| 4 | 渲染耗时 | P95 **860 ms** < 1,500 ms | **PASS** |
| 5 | 峰值内存 | 峰值 **1,521.8 MB** > 512 MB；首次渲染即 610.9 MB | **FAIL** |
| 6 | 输出体积 | **0.468 MB** < 1.5 MB（子集化生效） | **PASS** |
| 7 | warnings 可接受 | **0 条** | **PASS** |
| 8 | 构建通过 | Next 16.2.6 + Turbopack 构建成功，**零 webpack 配置** | **PASS** |

判据 2、3 需真人操作浏览器与 Acrobat，本轮未做，如实标为未验证；它们不影响结论——判据 5 已单独构成 FAIL。

### 为什么判据 5 的失败是决定性的

内存开销**与文档规模、用字数量都无关**：

| 文档 | HTML | 不同汉字 | 首次渲染 RSS | 峰值 RSS |
|---|---|---|---|---|
| 极小（342 B） | 342 B | 17 | 578.9 MB | 867.1 MB |
| 真实中文简历 | 8.9 KB | 494 | 643.3 MB | 1,260.4 MB |
| 完整 fixture | 53 KB | 2,271 | 647.6 MB | 1,267.8 MB |

一份 **342 字节、17 个不同汉字**的文档首次渲染就吃掉 578.9 MB。这不是"2,000 字用字的极端情况"，而是**注册字体后每次渲染的固定代价**。

开销的来源经对照实验定位为"注册了字体"而非"中文"：不注册字体时开销完全平坦（85 MB，不增长）；注册 1.0 MB 的纯拉丁字体后单次约 35 MB 且逐次累积；注册 9.3 MB 的中日韩字体后单次约 320 MB。`auditContent`、`lang` 等选项均不影响该行为，故不是测量方式造成。

更关键的是 RSS **从不回落到基线**：12 次连续渲染中，第 2 次之后的最低 RSS 为 849.1 MB，峰值随渲染次数单调上升。长驻服务中内存不收敛，而是随已处理请求数持续增长——对 ADR-0007 描述的常驻渲染单元而言，这比"一次渲染偏重"更严重。

### 判据之外的附带发现（不改变判定，但需记录）

**A. `font-family` 声明在 `<html>` 上被静默忽略。** 引擎把 `<body>` 当作独立布局根，因此声明在 `<html>`/`:root`/`html > body` 上的可继承属性都进不了 `<body>`，且**不产生任何告警**；`body{}`、`div{}`、`p{}`、`*{}` 则正常。已用 `html{good}` + `body{unregistered}` 的对照确认：body 上的值干净地作用于全部后代，说明 html 上的值根本没参与继承。真实模板常把 `font-family` 放在 `html`/`:root`，这类模板会**静默产出整篇 `?` 的 PDF**——与引擎"everything outside the subset is named, never silent"的设计承诺相矛盾。

**B. HTML 路径与 React 路径的字体形状不同，传错时静默丢数据。** `@formepdf/html` 用 `{family, data, weight?, italic?}`；`@formepdf/next`/`@formepdf/react` 用 `{family, src, fontWeight?, fontStyle?}`。把 `data` 传给 React 路径时序列化器静默丢弃字体，随后由 Rust 侧报 `missing field 'src'`——错误信息不指向真正传错的属性。

**C. 无内建 CJK 回退。** 不注册字体时只用内建 `Helvetica`/`Helvetica-Bold`（`/Subtype /Type1`），汉字全部渲染成 `?`，输出无 `/ToUnicode`，并产生逐字的 "render defect" 告警。

### 结论与后续

- **不采用 Forme 作为终态引擎**，按预注册规则走 ADR-0001 分支二（headless Chromium）。中文提取能力本身是合格的（判据 1、6、7 干净通过），失败点在内存，且是固定且不收敛的代价。
- **不接受 ADR-0001「后果」一节里那条 Forme 特有风险**（pre-1.0 单维护者依赖、需精确锁版本），因为该分支未被选中。
- **测试材料已固化为常驻回归用例**：`.scratch/resume-platform/fixtures/`（含文档、生成脚本、原始测量证据与 `RESULTS.md`）。无论最终引擎是哪个，"中文可提取"都由此持续验证。
- **Chromium 的中文字体方案**须满足本 fixture 的全部字集：Windows 上 `simhei.ttf` 实测覆盖全部 2,271 个不同汉字（0 条缺字告警），可作为自带字体候选；容器镜像中需自带并显式注册。详见工单 03。
- 判据 5 的失败**不等于**"Forme 不可用"：若将来版本修复了内存行为，本 fixture 与测量脚本可直接复用重新裁定；届时再决定是否重开 ADR-0001。
