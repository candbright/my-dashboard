# ADR-0003：结构化内容模型；frontmatter 降级为交换格式

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0004（展示态）、ADR-0006（迁移）、ADR-0007（渲染服务）

## 背景

简历内容当前分散在**两处**，且**由两套解析器各自解释**：

| 位置 | 内容 | 谁来解析 |
|---|---|---|
| 磁盘 `{uuid}.md` 文件 | YAML frontmatter + Markdown 正文 | 前端 `gray-matter` + 自有章节切分；后端手写 `parseFrontmatter` |
| `resumes` 表列 | `name` / `job_title` / `email` / … / `summary` | 后端从 frontmatter 抽取后落库 |

### 已经发生的漂移与缺陷

1. **两套 frontmatter 解析器。** 后端那套是手写的 `key: value` 逐行解析——**无引号规则、无嵌套、无转义**。前端那套是完整的 YAML 实现。同一份文件在两端可能解析出不同结果。
2. **YAML 转义缺陷。** 前端拼接 frontmatter 时不加引号，值中含 `:` 或 `#` 会产出非法 YAML，导致简历**回读失败**。
3. **摘要被重复实现。** 后端 `extractSummaryFromMarkdown` 按章节标题（`## 关于我` / `## 简介` / `## About` / `## Summary`）抓摘要，**与前端解析逻辑是两套独立实现**。
4. **结构化字段编辑不可能。** 因为 `PUT` 只接受整份 Markdown，且后端会**从 frontmatter 重新推导所有元数据列**——任何直接改列的表单编辑都会被下一次保存静默覆盖。

### 这些缺陷共同阻塞的功能

- 「项目经历 vs 工作经历」自动区分（需服务端可靠理解章节语义）
- JD 关键词命中/缺失分析（需字段级结构化访问）
- 字段级版本历史与差异（需知道"哪个字段变了"）
- 服务端索引与搜索（需可查询的值）

**根因不是某个解析器写得不好，而是"同一份数据有两个权威"这个结构本身。**

## 评估过的选项

| 选项 | 说明 | 否决理由 |
|---|---|---|
| **A. 维持现状** | Markdown 是唯一权威，两端各自解析 | 上述功能**无法可靠实现**，每次都要重新猜 |
| **B. Markdown 为编辑对象 + 服务端持久化结构化快照** | 用户仍编辑 Markdown；保存时服务端解析并落库；前端消费快照 | **采纳。** 保留 Markdown-first 定位，同时获得可查询、可服务端校验的权威形态 |
| **C. 结构化数据成为权威，Markdown 退化为导出格式** | 用户改表单不写 Markdown | 砸掉"Markdown 编写"这一核心定位（README 首条功能） |
| **D. 前端解析后把结构 PUT 给后端** | 后端只存不算 | 把权威交给客户端，无法服务端校验与索引 |
| **E. 元数据进列，正文留在 Markdown，frontmatter 仅作交换格式** | 即 **B 的彻底形态** | **采纳（B 的具体化）** |

## 决策

**采用 B 的彻底形态（选项 E）。**

### 1. 三处职责的重新划分

| 内容 | 存放位置 | 权威 |
|---|---|---|
| **简历元数据** | `resumes` 表列 | **数据库**。UI 用表单直接编辑列，不经 Markdown |
| **简历文档**（章节、条目、要点） | 磁盘 `{uuid}.md`，**不含 frontmatter** | Markdown 文件本身。用户直接编辑 |
| **展示态** | `resumes.presentation` JSONB | **数据库**（ADR-0004） |

### 2. frontmatter 的降级

**YAML frontmatter 从"运行时结构"降级为"导入导出的交换格式"。**

- **导入**：接受带 frontmatter 的 `.md`，解析其元数据并写入列。
- **导出**：产出带合法 YAML frontmatter 的 `.md`，**用真正的 YAML 序列化器**（而非字符串拼接），保证特殊字符被正确引用。
- **运行时**：**任何代码路径都不再依赖 frontmatter 来获取元数据。**

### 3. 解析器收敛

**服务端解析器成为唯一权威。** 前端保留的解析能力**仅限正文**（章节标题、条目、日期），且明确声明为**非权威**——它存在的唯一理由是编辑时的乐观 UI 需要即时预览，不能每键往返服务端。

元数据解析**从关键路径上彻底移除**。

### 4. 后端必须在保存时产出结构化快照

`PUT` 保存简历文档后，服务端解析并：
- 更新派生的元数据列（若正文含可推导信息）
- 计算并存储 `summary`
- 记录字段级变更（供 ADR-0010 的版本历史使用）

## 后果

**正面**
- **YAML 转义缺陷从根上消失**——不再从 frontmatter 读运行时结构，就不存在"拼坏 YAML 导致回读失败"。**这个 Bug 不需要被修，它被移出了关键路径。**
- 元数据可**逐字段编辑**，不再被下一次保存覆盖。
- 「项目经历/工作经历」区分、JD 匹配、字段级历史、服务端搜索全部解锁。
- 两套解析器的漂移风险收敛为"一套权威 + 一套声明为非权威的预览实现"。

**负面 / 代价**
- **需要数据迁移**：把存量简历 frontmatter 中的元数据抽进列，并从 `.md` 文件中剥离 frontmatter。属破坏性变更，须走 ADR-0006 的迁移器并**先备份**。
- 中文特有字段（政治面貌、籍贯等）需要在 `resumes` 表新增列或改用扩展表——见 ADR-0006 与阶段二。
- `resumes` 表的列数会显著增长；须同步处理 `AutoMigrate` 的四个改动点（model / 领域结构体 / 两个转换器）。
- 前端 `ParsedResume` 类型与旧解析器将逐步退役，期间存在**双模型并存**的过渡期。

**受影响的既有代码**
- `src/lib/resume-parser.ts`、`src/lib/resume-builder.ts`（前端解析与拼装）
- `kratos-server/internal/biz/resumevault/resume.go` 的 `parseFrontmatter` 与 `extractSummaryFromMarkdown`
- `src/components/ResumeEditor.tsx`（元数据编辑改为表单编辑列）
