# ADR-0008：视觉模板；首套必须 ATS 安全

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0001（渲染）、ADR-0004（展示态）、ADR-0005（ATS）

## 背景

项目有约 **12 个"模板"**，分布在 `src/lib/resume-templates.ts`，按类别分组（通用/技术/商务/创意/法律/教育），每套带名称、描述、分类、强调色。

**但它们不是视觉模板——它们只是内容种子。**

`ResumeTemplate` 接口的 `markdown` 字段是**示例内容**。所有模板**共享同一套渲染**（`ResumeDisplay` 与 `ResumePrintView` 各只有一种设计）。

结果：用户选择"UX 设计师模板"，**只换掉了示例文字，视觉上完全没变**。

### 行业基准

| 项目 | 视觉模板数 | 机制 |
|---|---|---|
| Reactive Resume | **17** | `packages/pdf/src/templates/<name>/`，每套是 React 组件，自带 `semantic.ts` 描述 CSS 钩子 |
| JSON Resume | **52** | npm 包 `jsonresume-theme-*`，**注册表机制**，社区贡献 |
| RenderCV | 8+ | **主题是 YAML 设计覆盖层，不是代码** |

### 同时存在的硬约束

由 ADR-0005 引用的行业数据：**双栏布局导致 17.2% 的内容在 ATS 中丢失**，**装饰性图标导致 10.6%**，联系方式置于页眉带 4.1%。

而 Canva 最热门的简历模板**恰恰是双栏 + 照片 + 图标**——即 ATS 最差的组合。

**因此"多套好看模板"与"ATS 可读"存在真实冲突，不能假装它不存在。**

## 决策

### 1. 模板成为「渲染器 + 样式 token」

`ResumeTemplate` 从"内容种子"改为**渲染定义**：

- **渲染器**：如何把结构化内容排成页面
- **样式 token**：主色、字体族、字号缩放、行距、页边距的默认值（用户可在展示态中覆盖，ADR-0004）

**内容种子与视觉模板分离**——"示例内容"是模板的附加属性，不是它的本质。

### 2. 首套模板必须是 ATS 安全款

**第一套实现的视觉模板固定为：**

| 属性 | 值 |
|---|---|
| 栏数 | **单栏** |
| 装饰性图标 | **无** |
| 联系方式位置 | **正文区顶部**，不进页眉带 |
| 版式表格 | **不用** |
| 字体 | **必须嵌入并子集化** |

依据 ADR-0005 引用的数据集归因——这四项正好对应丢失率最高的前四类。

**顺序是刻意的**：先做安全款，再做设计款。反过来会导致用户默认选择好看的那套，然后在 ATS 里悄悄丢内容。

### 3. 每套模板必须标注「解析友好度」

在模板卡片上标注 **高 / 中 / 低**，让用户**知情选择**。

| 友好度 | 特征 |
|---|---|
| **高** | 单栏、无图标、联系方式在正文、无版式表格 |
| **中** | 单栏但含装饰元素，或双栏但内容分区清晰 |
| **低** | 双栏 + 图标 + 照片 + 版式表格 |

**这是零后端成本的信任设计**，且目前无人明确在做。它把"我们为你的 ATS 结果负责"从口号变成了界面元素。

### 4. 模板库按「用途」分面，而非视觉风格

分面维度：**校招 / 社招 / 实习 / 留学 / 考研复试 / 内推**，并可加 **1 栏 vs 2 栏**（ATS 安全）筛选。

依据：五百丁按 岗位 2,599 / 用途 165 / 院校 668 / 语言 80 / 风格 90 索引，**「用途」远重于「风格」**；超级简历按求职阶段/赛道分类。Zety 最高杠杆的库控件正是"1 栏 / 2 栏"筛选。

### 5. 模板数量不作为竞争维度

市场从 4 套到 10,000 套都有。VisualCV 只有 30+ 套却是功能面最强的产品之一。

**长期机制是注册表**（JSON Resume 用 52 套主题证明了它）：任何人发布一个符合接口的实现即可上架。**短期不实现注册表，但接口设计要允许它。**

## 后果

**正面**
- 用户选模板**第一次真的会看到不同**。
- ATS 安全款默认存在，且用户能看见自己在做什么取舍。
- 展示态（ADR-0004）与模板天然衔接：模板提供默认值，用户可覆盖。
- 按用途分面比按风格分面更贴合真实求职场景（尤其国内）。

**负面 / 代价**
- **这是本计划中最大的单点工作量**：从"一套渲染"变成"渲染器 + N 套实现"。
- 每套模板都要在**两个渲染路径**上验证（编辑器近似预览 + 渲染服务权威产出）——如果 ADR-0002 的 Spike 选了 Forme 则是一套代码，选 Chromium 则要小心 CSS 在两处的差异。
- "解析友好度"标注需要人工判定，且**判定标准必须写下来**，否则会变成随口贴标签。
- 双栏设计款做出来后，用户可能选它并在 ATS 中丢内容——**标注是唯一的缓解**，无法根治。

**受影响的既有代码**
- `src/lib/resume-templates.ts`（接口重构）
- `src/components/TemplateSelector.tsx`（分面筛选 + 友好度标注 + 视觉预览缩略图）
- `src/components/ResumePrintView.tsx`、`ResumeDisplay.tsx`（拆分为模板渲染器）

## 实施记录（工单 20，2026-10-15）

工单 20 实现了前两套模板（`ats-safe-single-column` 高 / `classic-centred` 中），并把
`resume-templates.ts` 拆成三层：**模板**（`resume-template.ts` + `components/resume-render/`）、
**内容种子**（`resume-template-seeds.ts`）、**起步项**（`resume-starters.ts`，把种子 + 模板 + 强调色
配成 12 个入口）。下面只记录决策的落地结论，以及实施中发现的、本 ADR 没有预见到的东西。

### 令牌生效的判定：字段级，而不是对象级

这是本次实施中**唯一一个"看起来正确、实际是死代码"的缺陷**，值得写下来，因为它有两层。

模板 token 要成为页面的基线，直觉写法是调用点合并：

```ts
accentColor: stored.accentColor ?? template.tokens.accentColor
```

**这永远不会生效。** `presentationFromRecord`（ADR-0004）的职责就是填满每个字段，所以它返回的值
没有任何 nullish 成员，`??` 右侧成为死代码。每套模板都会渲染成同一种棕色，而断言"token 已声明"
的测试全部通过——**只有把两份简历并排看才会发现**。这正是本 ADR 要修的缺陷
（`模板看起来不同，实际相同`）在下一层重演。

第二层更隐蔽：读接口对"什么都没存的简历"并不返回 `null`，而是返回**与 `DEFAULT_PRESENTATION`
逐字段相等的完整对象**。因此"用户没存过"和"用户存了默认值"是同一个载荷，**对象级**的判定
（"存过东西就让用户赢"）无法区分它们——那样 token 依然是死的。

**结论：判定必须在字段级**——某个字段仍等于默认值，就说明它不携带意图，模板的意见更具体；
某个字段与默认值不同，就是用户的选择，用户赢。代价是**用户无法把某个字段显式设回默认值来否决
模板**。这个方向是对的：反过来选，失败模式是一个"任何模板都不起作用的模板系统"。

### `photo` 是合并，不是二选一

"用户选了照片"和"模板要照片"是两件独立的事，所以 `photo` 不参与上面的字段级取舍：

- 任一侧给出 `path`，就沿用；
- `enabled` 从**原始存储值**读取，而不是从解析后的展示态读。原因是解析必然是有损的——
  "已启用但没有图片"会被丢弃（否则渲染出坏图），而这恰好抹掉了"用户打开了照片、还没选文件"
  这个意图，它正是这个字段存在的全部内容。

### 模板数量与注册表

接口已按 §5 的要求留出注册表位置：`ResumeTemplate` 是纯数据 + 纯函数 `render`，
`RESUME_TEMPLATES` 是一个数组，`findTemplate(id, templates)` 接受注入的注册表。
`resolveTemplate` 只依赖传入的那一个模板对象，不读全局。

**增加一套模板是两侧改动**：`PRESENTATION_TEMPLATES` 是服务端闭集（ADR-0004 拒绝未知模板），
TypeScript 联合类型与服务端列表必须一致，否则 `resume-presentation-parity.test.ts` 失败。

### 新增：模板渲染器必须是 `TemplateRendererInput` 的纯函数

不能有 hook、不能读 context、不能依赖 Tailwind 颜色类或 CSS 自定义属性。原因有两个，
都不是风格问题：

1. 同一段代码要在**两个渲染路径**上跑（本 ADR「后果」一节的要求），阶段 4 的渲染服务是
   Node + headless Chromium，没有 React 运行时之外的任何环境。
2. 打印走的是自包含 iframe，`var(--color-primary)` 在那里解析不到任何值——旧代码的字体栈
   一直静默回退到默认字体，就是这个原因。所有值以**内联样式 + 字面量**到达标记。

### 顺带发现、未修复，归属后续工单

- **打印路径绕过 `ResumeMarkdown`**：`**粗体**` 与 `[链接](url)` 会以字面量进入 PDF。真实缺陷，
  不在工单 20 范围内。

### 分页：一个「看起来正常、页数错误」的缺陷（工单 21 修复）

工单 20 的分层结构**破坏了分页**，而这个问题在本 ADR 初稿里被低估成"分页单位不匹配，归工单 21"。
实际后果比这严重得多，值得单独记一段，因为它是本项目至今**最隐蔽**的一个缺陷。

`flattenPrintFlow` 把打印根的**每个直接子元素**当作一个不可分割的块。模板分层后，打印根的直接子元素
只剩下 `header`、`hr` 和**一个章节 stack**，于是：

- 整份简历是**一个**测量块，高度必然超过一页；
- 被判定为 `hasOversizedBlock`，独占一页；
- 不报错、不崩溃、布局完全正常，**只有页数不对**。

**全部既有测试都通过了**，原因值得记住：`export-pdf.test.ts` 的用例手工搭 DOM，而手工 DOM 里章节就在
打印根下面、条目就在章节下面——手写结构永远符合代码的预期。`npm run verify:print` 同样用手写 HTML，
也看不见。这正是**为什么验收必须跑在真实产物上**，而不是跑在"与代码预期一致"的构造上。

修复与由此确立的约束：

1. **容器用 `data-print-flatten` 声明自己是透明的**（只为排版而存在），遍历时下钻而不是测量它。
   三个 stack 都带这个标记，`flattenPrintFlow` 改为递归。缺少标记的容器会被当成不可分割的块。
2. **分页的单位是条目**。回归测试渲染**真实组件**再遍历它，见 `export-pdf.test.ts` 的
   `flattenPrintFlow against the real print view`。
3. **条目间距用 CSS margin**（`.resume-entry + .resume-entry`）而不是 flex `gap`：分页逐个测量条目，
   而 `gap` 属于容器，不计入任何条目的高度，会让页面被塞入实际放不下的内容。
4. 新增 `npm run verify:template`，渲染真实组件并在真实浏览器里测量。它与 `verify:print` 的差别
   （手写 HTML vs 真实组件）已写入 `AGENTS.md`。

## 实施记录（工单 22，2026-10-15）：分面、标注与画廊

「按用途分面」（§4）与「标注解析友好度」（§3）在工单 20 已落地；工单 22 补齐**缩略图**与**可见的判定
标准**，并修掉分面筛选里两个"看起来在工作、实际不工作"的问题。以下两条是对本 ADR 的**具体化**，不是
改动：

### §3 的判定标准现在是代码里的单一事实来源

判定表移入 `src/lib/resume-parseability.ts`，画廊把它**印在界面上**（原生 `<details>`，无需 JS）。理由
就是 §3 自己的话：标注若不对照一张写下来的表，就从"对产品的声明"退化成"评审当天的心情"。测试断言该表
**覆盖 `TemplateParseability` 允许的每一个评级**，所以新增一个评级却忘了写判据会直接失败。

界面上的措辞刻意具体——「单栏」「无版式表格」而不是「结构清晰」——因为后者正是那种能让一个带表格的双栏
版式混过「高」的形容词。

### §4 的分面：能被声称 ≠ 能筛选

原实现列出**任一** starter 声称的分面，于是「单栏」出现在筛选栏里，而 12 张卡片**全部**是单栏：点击它
是一次看起来像控件、实际是空操作的交互。这与 §4 想避免的旧「行业分类」是同一类缺陷——六个按钮全是空
操作。

**新规则：全部卡片都声称的分面不做成按钮，而是用一句话说明为什么没有。** 尤其是列数：`two-column` 在
`TEMPLATE_FACETS` 里存在，但当前 registry 里没有任何模板声称它，所以界面上明写「目前所有模板都是单栏，
没有双栏模板可选」——§4 把 1 栏/2 栏列为最高杠杆的库控件，它的缺席必须被说明而不是静默。将来加入双栏
模板，`two-column` 会自动开始出现，这段代码不需要改。

### 缩略图：渲染，而不是贴图

风格徽章与分面都会**撒谎**——它们描述设计，但不展示设计。所以卡片上加视觉预览，且预览由**模板自己的
渲染器**画出，不用预导出图片：图片与渲染器会漂移，而图片**没有办法被测出来过期**。画廊展示上一版设计
比不展示更糟，因为它错得很自信。

做法是真实 794px A4 页面（`mode: 'screen'`）套 `transform: scale(256/794)`，再用 `overflow: hidden` 取
页面顶部。**不重新用小字号渲染**——那会改变换行位置，预览就不再是任何东西的预览。每张卡片用同一份示例
文档：用 starter 自己的内容会让预览展示的是**内容**，而内容正是用户马上要替换的；卡片之间真正不同的是
主色与模板，预览就只变这两样（`accentColor` 恰是两份模板的 tokens 都没有设的字段）。

## 实施记录（工单 48，2026-10-15）：模板优先的创建流程

工单 48 把创建改成三步——**① 选风格 → ② 定内容 → ③ 编辑预览并保存**——并把创建时的展示态与正文放进
**同一个请求**。它落实的是本 ADR 已写下的两条声明（模板是渲染器而不是内容种子；第一套必须 ATS 安全），
同时证明第三条声明此前**只存在于文档里**：「判定必须在字段级」那段合并代码在全仓**没有任何调用点**。

### 创建即写展示态：一个请求，字段是 JSON 字符串

创建路由 `POST /api/resumes` 原本只收正文，样式必须另发一次 `PATCH .../presentation`。两步的失败模式很
具体：用户在向导里选了配色，保存成功，然后样式没跟上——或者第一次 `PATCH` 失败，得到一份"保存了但不是我
选的样子"的简历，而屏幕上没有任何东西说明这件事。所以展示态随创建一起提交（ADR-0004 的 JSONB 列不变，
数据层不变）。

它走 multipart 的 `presentation` 字段，值是一段 **JSON 字符串**而不是 JSON 请求体：该路由已经是
multipart（主输入是文件或文本），前端两条路径都构造 `FormData`，为了样式再引入第二种内容类型没有收益。

三条边界是刻意的：

1. **字段缺失或为空 ⇒ 服务端默认值**，不是 400。这是向后兼容分支：字段出现之前写下的每个客户端、以及不
   关心样式的脚本，仍然是一次合法创建。它也是前端回归的落点——向导若停止发送样式，创建照样成功，用户的
   选择**静默消失**。
2. **创建不接受 `version`**。`version` 的语义是"我读过这一行，它必须还在"（ADR-0010），新建的行没有这个
   承诺可兑现；接受并忽略它会让客户端以为检查过锁。它作为未知字段被拒（400 `INVALID_PRESENTATION`），与
   更新路由共用同一个错误映射函数，两条路由对同一缺陷不会给出不同代码或不同措辞。
3. **未知模板/未知字段 ⇒ 400**，且消息点名出错字段。理由是 ADR-0004 已经写下的那条：未知键被静默忽略时，
   用户改了颜色、界面报告成功、什么也没发生，而且**没有任何证据可查**。

### 模板数量：只能追加，不能插入

`PRESENTATION_TEMPLATES` 是服务端闭集，TypeScript 联合类型与它逐字对齐，由 `resume-presentation-parity.test.ts`
对着**从 Go 常量生成**的 fixture 断言。所以新增一套模板必然是两侧改动——这正是本 ADR §「模板数量与注册表」
要求的。补一条工单 48 发现的具体约束：**新 id 只能追加在末尾**。闭集的顺序就是画廊的顺序，而"第一项即默认"
（空白模板 = 第一项）依赖它；把新模板插到中间会静默重排每一位用户的选择器。绿野通栏因此排在末位，
`ats-safe-single-column` 仍在首位。

### 新模板「绿野通栏」（`verdant-banner`）：一个被实测推翻的验收要求

单栏、无衬线、鼠尾草绿通栏页眉（含蓄的同心圆装饰）、反白姓名与联系方式、主色侧边线小标题、技能标签、
右对齐日期。解析度判为**中**：单栏但含装饰元素；联系方式是**色块上的 DOM 文本**而不是图形内的文字，
每个值仍带标签（`Email：…`），文字层可抽取——代价是纯图像式解析器会丢失位置信号。

页眉文字的颜色原本被要求"固定用一个浅暖色，并说明它对每种允许的主色都安全"。**这个要求是错的，实测推翻了
它**：用户可在六色板中任选主色，而在最浅的暖棕 `#d4a373`（相对亮度 0.414）上，**没有任何浅色前景**能超过
2.26:1（纯白也只到那里）——暖奶油 `#faf6f1` 实测 2.10:1。第一版用一个 `text-shadow` 去补偿，那是在为一个
不该存在的约束打补丁。现在改为：在两个**合规暖色墨**（`#faf6f1` / `#292524`）之间按实测对比度择优
（`bannerInk`，纯函数），不用第三种颜色、不用纯黑纯白。最差情形是森林绿 `#557a46` 上的 **4.58:1**（奶油胜），
六个主色全部达到 AA 正文标准；AAA 用两种暖墨不可能达到，所以没有声称。

### §「判定必须在字段级」终于接上了——它此前只写在文档里

本 ADR 第 120–131 行描述的缺陷（`presentationFromRecord` 填满每个字段，于是模板 tokens 成为"看起来活着的
死代码"，每套模板都渲染成同一种棕色）在工单 20/22 修的是**库**，而渲染路径从未调用过它：
`ResumePrintView`（编辑器预览与 `export-pdf` 共用）只做 `presentationFromRecord(resume.presentation)`。
实测证据：`{schemaVersion: 1, template: 'verdant-banner'}` 渲染出的是**默认石棕 + 衬线**，绿野通栏的
sage/sans 从未到达预览或 PDF，`classic-centred` 的 `lineHeight`/`pageMargin` tokens 同样如此。这正是
「模板看起来不同，实际相同」在下一层的重演，也说明**只把规则写进 ADR 并不算修好**。

修复是把渲染路径接上已存在且有测试的合并：`presentationFor(templateForPresentation(presentationFromRecord(stored), RESUME_TEMPLATES), stored)`
（字段级取舍 + `photo` 合并 + 未注册 id 回退到第一套）。现在有测试钉住它：只命名 `verdant-banner` 的记录渲染出
`#8b9d77` 而**不是** `#5c4033`，并且同一条路径产出 verdant 的 `ui-sans-serif…` 字体栈与 `classic-centred` 的
衬线栈——后半条是坏掉的合并无法伪造的。

顺带更正上一条记录里的一句：`accentColor` 已**不是**"两份模板的 tokens 都没有设的字段"。绿野通栏的 token 主色
就是鼠尾草绿，缩略图与预览都按"tokens 提供默认、用户改动胜出"解析。

### `photo` 是合并：模板不得吞掉用户的开关

§「`photo` 是合并，不是二选一」现在有了实现：开关从**原始存储值**读取，所以"用户打开了证件照"这件事不会
被模板的沉默抹掉；`path` 优先取展示态、其次取元数据头像。绿野通栏在开关打开且取到图源时，把证件照画在通栏
右侧（奶油描边、有机圆角），关闭时**不保留任何位置**（DOM 与之前逐字一致，装饰带由色块移到文本列，因此
"装饰不会压到证件照"是结构性的而不是两个数字恰好不重叠）。实测：证件照 94×122 位于 657px 通栏内，装饰的
**实际绘制区**与文字、与证件照的交集均为空。解析度仍是中：低判据里的"证件照"指的是模板**自带**证件照位，
用户打开的证件照不移动这个评级。

### 内容与风格彻底分开：案例参考

本 ADR 的核心声明是「模板是渲染器，不是内容种子」。工单 48 把旧概念 `ResumeStarter`（一份示例文档**加**
一个默认模板）从创建流程里去掉，改名「案例参考」，并让种子卡片**不带**版式预览：种子的职责只是给一份可编辑
的内容，风格由上一步决定。`lib/resume-starters.ts` 与其 `ACCENT` 色板已删除，六色板唯一来源是
`PRESENTATION_PALETTE`（与 ADR-0004 的服务端闭集对齐）。

### html 解析视图保持独立

创建流程的预览不再解析 HTML 展示态，而是渲染**用户选中的模板**；解析视图（`ResumeDisplay`，含个人信息头部）
保留为**已创建简历**的独立视图 `/resume/[slug]`。两者不是同一个东西：一个回答"它会印成什么样"，另一个回答
"平台从这份文档里读到了什么"。

### 验证门禁现在覆盖每一套模板（此前只覆盖第一套）

`npm run verify:template` 是本 ADR 要求"新增/修改模板必须跑"的那道门禁，但它此前只渲染 ATS 安全模板——
也就是说**新渲染器没有任何浏览器门禁**，而它存在的全部理由（工单 20 的"整份简历静默变成一块"）恰好发生在新
渲染器上。现在它遍历 `RESUME_TEMPLATES`，用一个覆盖用例断言 `RESUME_TEMPLATES` / `TEMPLATE_METADATA` /
`PRESENTATION_TEMPLATES` 三者 id 集合相同——注册了却没被验证的模板会让门禁失败。三套模板全部通过（约 20s），
工单 20 的 ATS 断言一条未放松；对标注「中」的模板，只适用于「高」的检查会打印 `SKIP` 与原因，使覆盖范围可审计
而不是静默消失。顺带修掉一个门禁自身的缺陷：孤立标题的正则只匹配一种标题形状（不含 `style` 属性的 `<h2>`），
**它一直在静默地不匹配**，于是"标题被孤立在页尾"这类失败当时看不见。

### 顺带发现、未修复，归属工单 49：分页不预留重复页眉的高度

分页把页眉从流里取出、由 `buildPrintDocument` 重新印在**每一张**纸上，但 `paginateBlocks` 仍按**整页**
内容高度填流——等于把页眉的高度花了两次。实测（9 条目、18mm、`.resume-page` 固定 986px）：

| 模板 | 页数 | 页眉 | 每张纸溢出 | 越过下一张纸顶部 |
|---|---|---|---|---|
| `ats-safe-single-column` | 4 | 117.4px | 0 / 106 / 42 / 0 | — / 106.1 / 42.1 |
| `verdant-banner` | 4 | 197.0px | 0 / 352 / 57 / 0 | — / 351.9 / 56.7 |

**这是既有缺陷，不是绿野通栏引入的**（ATS 模板同样中招），但 197px 的通栏把它放大 3.3 倍；且溢出多于页眉
高度（352 − 197 = 155px），差额与 `ResumeSectionList` 用 flex **`gap`** 排布章节间距一致——与 AGENTS.md 对
条目间距写下的规则（用 CSS margin，不用 `gap`，因为 `gap` 属于容器、不计入任何块的测量）同一个原因。
门禁看不见它：它数**页数**而不看**像素**，被裁掉的纸页数仍然正确、文字层仍可抽取。已在工单 49 单独跟踪。

### 复验（真实前后端都在运行，2026-10-15 晚）

上一条记录是**在测试替身下**走查的（后端未启动，`/api/auth/me` 与创建接口被路由拦截）。两个项目重启后
（kratos-server 用当天源码重新编译，`next dev` 清掉 `.next`），同一条链路在**不拦截任何请求**的条件下又走了
一遍，查出两处只有真实环境才会暴露的缺陷，都已修复并各自留了工单：

1. **保存的模板到不了详情页**（工单 50）。ADR-0004 把展示态放在**记录旁边**（`ResumeInfo` 没有该字段），
   而组件读的是 `resume.presentation`，边界上没有人折叠——`presentationFromApi` 在生产代码里**一次都没被
   调用过**。于是向导第 3 步的预览是对的（它传的是尚未保存的展示态），保存之后从记录读回来的那一路却渲染
   成默认模板，而且**不报错**。同一个洞还让 `PUT` 回复后的整体替换把屏幕上的样式清成默认。
2. **CJK slug 被编码两次**（工单 47 的补充节）。`params.slug` 交来时**仍然是百分号编码的**，页面又
   `encodeURIComponent` 了一次，于是中文 slug 的简历在详情页答「页面不存在」——后端其实找得到这一行，
   只是没找到被发过去的那个 slug。ASCII slug（`resume`）掩盖了它，这正是本工单的模板示例与既有测试都没
   抓到它的原因。

### §2 「模板改变的是 UI 风格」需要一句落地的约束

上面第 1 条值得写在这里：**「保存了某种风格」必须在读回来的路径上被证明**。渲染器是纯函数、向导预览也
正确，都不能说明一份**已保存**的简历会用它——展示态是**兄弟字段**而不是记录的一部分，前端必须显式折叠
（`resumeWithPresentation`）。这是 §2 与 ADR-0004 的交界处，两者各自的测试都覆盖不到。
