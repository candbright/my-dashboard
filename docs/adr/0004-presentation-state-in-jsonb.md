# ADR-0004：展示态存 JSONB 列

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0003（内容模型）、ADR-0010（版本与乐观锁）

## 背景

有一类信息**不影响内容语义，只影响渲染结果**：模板选择、主色、字体、字号缩放、行距、页边距、章节顺序、证件照。

它必须有地方存。当前**无处可存**——所有渲染细节都是硬编码的。

### 候选项：Markdown frontmatter

看似自然（单文件自包含、可 git diff），但有一个具体障碍：

- 后端 `PUT /api/resumes/{id}` 只接受 `{markdown, visibility}`。**改一个颜色就得重写整个文档。**
- 更糟的是这两个字段在同一请求里**互斥**——`visibility` 分支会提前 `return`，**静默忽略同请求里的 `markdown`**。
- ADR-0003 正在把元数据移出 frontmatter，再把展示态塞回去会造成语义混乱。

**展示态本质是偏好而非内容。** 它需要独立更新、独立校验、可能需要独立 A/B。

## 决策

**展示态存 `resumes.presentation` 列，类型 JSONB。**

### 初始结构（示意，非最终 schema）

```jsonc
{
  "template": "ats-safe-single-column",   // 视觉模板 id
  "accentColor": "#5c4033",
  "fontFamily": "serif",                  // serif | sans
  "fontScale": 1.0,
  "lineHeight": 1.5,
  "pageMargin": "18mm",
  "sectionOrder": ["关于我", "工作经历", "项目经历", "教育背景", "技能"],
  "photo": { "enabled": false, "path": null }
}
```

### 约束

1. **必须服务端校验。** 只接受已知键与合法取值域；未知键拒绝而非静默忽略（避免"设了没生效"的静默失败）。颜色须符合设计规范——**冷色与纯黑应被拒绝**（`AGENTS.md` 硬禁止）。
2. **必须有版本演进策略。** JSONB 无 schema 约束，须携带 `presentation.schemaVersion`，并在读取时做向前兼容的迁移。
3. **不进入版本历史。** ADR-0010 的内容快照**只快照简历文档**，不含展示态——否则"换个颜色"会污染内容历史，让回滚语义变模糊。
4. **变更须走乐观锁。** 与内容共用同一 `version` 列，避免样式更新覆盖内容更新。

### UI 意愿

展示态由 UI **直接编辑**（样式面板），**不经过 Markdown**。

## 后果

**正面**
- 改样式不需要重写正文文件，也不会触发内容版本历史。
- 可独立校验（含设计规范约束），把"冷色调"这类违规挡在服务端。
- 可承载 A/B 与模板切换，而不产生内容 diff。
- 一个 JSONB 列替代了"N 个样式列"的膨胀。

**负面 / 代价**
- **"一份简历"变成两处真相**（文档 + 展示态）。缓解：两者语义清晰分立，且共用同一个 `version` 保证一致性。
- JSONB 无编译期类型安全，**校验逻辑必须显式编写并测试**。
- 若将来需要对展示态做查询（如"找出所有用某模板的简历"），需补 GIN 索引。
- 导出为 `.md` 时，展示态**无处安放**——须决定是省略，还是写入一个明确的 metadata 区块。**默认省略**（交换格式只承载内容），并在导出说明中告知。

## 实施记录（工单 19，2026-10-14）

本轮把本 ADR 落地为 `resumes.presentation` 列、服务端校验与独立更新端点。**样式面板 UI 与打印
渲染接线不在此**（见文末），本记录只覆盖决策本身的落实。

### 落实了哪些约束

**约束 1（服务端校验）**——`internal/biz/resumevault/presentation.go`，**严格写入、宽松读取**
两条路径刻意不对称：

- 写入用 `DisallowUnknownFields` **加**尾随 token 检查。只靠前者不够，它拦不住
  `{"a":1}{"b":2}`。
- 读取是**全函数**：存储值损坏或为 `NULL` 一律读成默认值、错误故意吞掉。读路径不该因为一个
  样式值把整页打不开——这是"宽松读取"的具体理由，不是偷懒。
- 冷色与纯黑按本 ADR 与 `AGENTS.md` 拒绝。**主色是封闭色板 + 设计规则两道独立检查**：
  `#ff0000` 明确是暖色仍被拒（不在六色色板内），色板内每一色都被接受。
- 冷色判定只在饱和度高于 `0.10` 时生效。HSL 给无彩色分配任意色相（0），不加这道闸，中性灰
  是否被判为冷色就取决于运气。
- 亮度下限 `0.20` 使 `#292524`（stone-800，L≈0.151）被拒。这**不**与 `AGENTS.md`
  「用 stone-800 替代纯黑」冲突：那说的是正文文字色，不是主色。测试里写明了理由。

**约束 2（版本演进）**——`schemaVersion` 缺失读作最旧形状并升级、更低版本升级、更高版本拒绝、
写出时盖当前版本。前端同样**总是**盖当前版本，从不回显存储值。

**约束 3（不进历史）**——`UpdateResumePresentation` 不调用 `recordVersion`；工单 16 已有的
`TestASnapshotIsContentOnly` 继续守着这条。`.md` 导出按本 ADR 的「默认省略」执行，并用类型签名
强制：`resumeMarkdownExport(metadata, body)` 收不到展示态，所以省略是结构性的而非靠自觉。

**约束 4（乐观锁）**——`WHERE id = ? AND version = ?`，`RowsAffected == 0` 判冲突。与内容共用
同一个 `version` 列，没有第二个计数器。

### 一处决策时需要记录的技术细节：键名拼写

本 ADR 与工单 19 都用 camelCase（`accentColor`）。落地时发现服务端**有两种编码器**，而选错哪
一种不会报任何错：

- `internal/server/http.go` 把默认响应编码器换成 `encoding/json` + 生成结构体 tag（此处
  protoc-gen-go 产出 **snake_case**）。只有 `writeJSON` 走这条路。
- `ctx.Result` **不走**它，走 kratos 的 JSON codec = `protojson` = **camelCase**。

资源上其余所有路由都用 `ctx.Result`，前端读的也是 camelCase。端点最初用 `writeJSON` 写回复，
会让面板拿到 `accent_color` 而它期望 `accentColor`，于是永远显示默认值且**不报任何错**。改为
新增 `UpdatePresentationReply` proto 消息 + `ctx.Result`。前端 `presentationFromApi` 同时接受
两种拼写，作为这种情况再次发生的兜底。

### 新增的负面后果

- **前端必须复制一份色板与边界。** 用户点了非法值应在往返之前被拒，所以前端需要自己那份常量。
  这份复制会无声漂移，且往最坏方向漂移（前端多留一个服务端已删的颜色 ⇒ 用户点它必然 400，
  而色块就在屏幕上）。缓解：`cmd/resumepresentation` 从活的 Go 常量生成 fixture，
  `resume-presentation-parity.test.ts` 逐项比对；漂移会导致测试失败。这仍是一份需要维护的复制。
- **前后端两套校验逻辑要靠 fixture 维持一致**，这是上一条的直接代价，不是免费的：校验规则
  本身在两边各写了一遍。

### 尚未实现

**样式面板与渲染接线。** 本 ADR 的「UI 意愿」说展示态由 UI 直接编辑——这仍然成立，但**何时**
交面板取决于它是否可见：面板的价值全在"改了就看得见"，而预览目前是一份硬编码排版的组件，
工单 20 才把它换成真正的渲染器（ADR-0007）。现在交一个改了没有任何可见效果的面板，比不交更
容易误导——用户会以为功能坏了。因此样式值的**可达性**交由工单 20/21（渲染与模板）与 22–24
承担，本 ADR 在本轮交付的是它们共同的前置。
