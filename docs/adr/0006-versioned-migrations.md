# ADR-0006：自研版本化迁移器

- **状态**：Accepted
- **日期**：2026-10
- **相关**：ADR-0003（数据迁移）、ADR-0010（版本列）、ADR-0009（索引）

## 背景

Schema 变更当前完全依赖 GORM `AutoMigrate`：每个模块的 `Migrate()` 就是一串 `db.AutoMigrate(...)`，**没有 SQL 文件、没有版本历史、没有回滚路径**。

### `AutoMigrate` 的三个硬局限

1. **不会创建 GIN / 表达式索引。** 而本项目即将需要：`resumes(visibility, approval_status)` 复合索引（`ListPublicApproved` 的主查询路径）、`pg_trgm` 模糊搜索索引。
2. **对非空表新增 `NOT NULL` 无默认值的列会直接让服务启动失败**——它发 `ALTER TABLE … NOT NULL` 但不做回填。
3. **无记账、无版本、无回滚。** 改错了只能手工写 SQL，且**无法知道当前库处在哪一版**。

### 即将发生的变更

| 变更 | 类型 |
|---|---|
| `resumes.version` 整数列 | 加列 + **回填** |
| `resumes.presentation` JSONB 列 | 加列 |
| 中文特有字段（政治面貌/籍贯/民族/…） | 多列 |
| `resume_versions` 表 | 新表 |
| `ai_usage` 表 | 新表 |
| `resumes(visibility, approval_status)` 索引 | **索引**（AutoMigrate 不支援） |
| `pg_trgm` 扩展 + 搜索索引 | **扩展 + 索引** |
| 存量简历 frontmatter → 列 | **数据迁移** |

这是**四张表级别**的变更，加上一次破坏性数据迁移。`AutoMigrate` 承载不了。

## 评估过的选项

| 选项 | 否决理由 |
|---|---|
| **A. `golang-migrate` / `goose`** | 引入外部二进制与一条**从没走过的部署路径**——这个仓库**连 docker-compose 都没有**，新增部署依赖的成本被低估 |
| **B. 保留 `AutoMigrate` + 严格约定** | 约定不会被执行；且它**根本创建不了 GIN 索引**，这是能力缺口而非纪律问题 |
| **C. 自研轻量迁移器** | **采纳** |
| **D. 维持现状 + 人工 SQL** | 在四张表级别的变更前不可接受 |

## 决策

**采用 C：自研轻量版本化迁移器。**

### 形态

- **一张 `schema_migrations` 表**记录已执行的迁移：`(version, name, applied_at, checksum)`。
- **迁移函数编译进二进制**——无需外部工具、无需新增部署依赖。
- **启动时按序执行**未应用的迁移，每条在**独立事务**内完成并记账。

### API 形态（示意）

```go
var migrations = []Migration{
    {Version: 1, Name: "add_resume_version_column", Up: func(tx *gorm.DB) error { ... }},
    {Version: 2, Name: "add_presentation_jsonb",    Up: func(tx *gorm.DB) error { ... }},
    // ...
}
```

### 与 `AutoMigrate` 的分工

| 场景 | 机制 |
|---|---|
| **全新部署** | `AutoMigrate` 建出基线 schema，随后迁移器把所有迁移标记为已应用 |
| **存量部署** | 迁移器从基线版本开始逐条应用 |
| **索引与回填** | **只走迁移器**（`AutoMigrate` 做不到） |

### 失败语义（Q34）

**迁移失败 → 拒绝启动**（fail-fast），日志给出**失败的迁移编号与原因**。

理由：这个后端**启动时本来就有一堆硬前置**——`AI_KEY_ENCRYPTION_SECRET` 未设置直接 `panic`、Postgres 不可达则起不来。因此"拒绝启动"不是新增的运维负担，而是**与既有风格一致**。

**被否决的失败语义**：
- **记录失败但继续启动**——最危险。半迁移的数据库配上能写入的服务，会持续产生错误数据。
- **自动回滚**——在数据迁移上**往往比不复滚更危险**（回滚可能丢数据，且无法保证回滚脚本本身正确）。
- **只读模式启动**——需要额外的中间状态逻辑，当前不值得。

### 强制约定

1. **迁移不可变。** 已发布的迁移一经执行不得修改；修正必须新增一条。
2. **`checksum` 校验**：启动时比对已应用迁移的校验和，不匹配则拒绝启动（防止有人偷改历史迁移）。
3. **破坏性迁移必须先备份。** 存量 frontmatter → 列的迁移属此类；须在迁移前落一份全库快照，并在迁移函数内**只做加法、不做删除**。
4. **`AutoMigrate` 保留但降级**为"基线建表"角色，不再作为日常变更手段。

## 后果

**正面**
- 索引、回填、数据迁移从"做不到 / 靠人工"变成**一等公民**。
- 任何时刻都能回答"这个库在哪一版"。
- 无需新增部署依赖——迁移是二进制的一部分。
- 子代理调查确认后端**已有 63 个 stdlib 测试**与良好的测试习惯，迁移器可以沿用同样的表驱动测试风格。

**负面 / 代价**
- **多了一套自己维护的代码**（估计数百行）。必须自己保证正确性——建议迁移器本身就有测试，且**第一条迁移就是 ADR-0010 的 `version` 列**，用它验证端到端流程。
- 无回滚脚本（有意为之，见失败语义）。**回滚靠备份恢复，不靠自动逆向迁移**——这一点必须在 `DEPLOY.md` 中写明。
- 需要一次性梳理存量部署当前的 schema 状态以确定基线版本。
