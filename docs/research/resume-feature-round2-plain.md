## 一、这一轮查了什么，和上一轮什么关系

上一轮调研回答的是"**这个产品该有哪些功能**"，结论已经变成了 44 个待办任务。这一轮不重复它，只补它没覆盖的三件事：

1. 有没有**外部强制要求**已经生效、而我们的计划完全没考虑到？
2. 这一年多来，同行有什么**新玩法**？
3. 有哪些**看着很诱人、但其实不该做**的事？

**一个重要发现**：翻遍项目文档和全部 44 个任务，**没有一处**提到"无障碍使用""个人信息保护""AI 内容标注"或"数据保留多久"。所以下面第一节不是重复劳动，是真正的空白。

## 二、必须先处理：三个已经踩线的问题

### 2.1 一份被文档点名、却从来没人建的"目录"

数据库里有一张大表存简历。系统经常要查"哪些简历是公开的、且已经审核通过的"。

这就像一本没有目录的书——每次要查，都得**从第一页翻到最后一页**。数据少的时候感觉不出来，多了就会明显变慢。

有意思的是：项目里负责数据库升级的那个文件，**自己的注释里就写着"这个目录需要手工建，自动工具建不了"**，但历次升级记录（1 到 4 号）里**没有一次真的建了它**。

更糟的是：上个月刚完成的一项优化（工单 09）为了显示"共几份"，让这个查询**从每次翻一遍变成每次翻两遍**。

**为什么必须修**：改动很小，但不修的话，简历越多越慢，而且**不会有任何提示**——用户只会觉得"这网站越来越卡"。

---

### 2.2 一次后台操作要发两百多条数据库查询

管理员有个"待审核列表"页面。打开一次，系统会**一份一份地**去查每份申请的详情，而不是一次性全部取回。

如果这一页显示 200 份申请，就会发出**最多 205 次**数据库查询。

**类比**：去超市买 200 样东西，不是推一辆车一次买齐，而是**结账 200 次**。人少的时候收银员还能应付，人多的时候整条队伍都堵住。

**为什么会这样**：代码是一份一份循环处理的，每一份都单独去问一次数据库。

**现状**：机制已经确认（我读了完整调用链），**但没有实测过它到底慢多少**——因为在开发机上数据太少，测不出真实差距。

---

### 2.3 一条验证码被原样写进了服务器日志

用户登录时收到的 6 位验证码，被**不加处理地记进了服务器日志文件**。

这行代码旁边**已经有一句"是不是开发环境"的判断**——说明写代码的人知道要区分环境，只是**这一行漏了**。

**为什么这条最危险**：验证码相当于一把能用 10 分钟的钥匙。任何能看日志的人——运维、日志收集系统、共用电脑上的同事——**都可以拿它直接登录别人的账号**。

**修它可能是这轮所有事情里最省事的**：改动就是一行。

---

### 2.4 顺带说三个"用起来会撞墙"的界面问题

这三处对普通用户没影响，但对**只能用键盘操作电脑的人**（包括视障用户）是硬伤：

**① 调整简历里章节的顺序，只能用鼠标拖。**

只能用鼠标把章节拖上拖下。用键盘**完全做不到**。而且我查过底层的动画库——**它压根没提供键盘方案**，不是我们配置错了。

**② 简历页面的内容，在没有 JavaScript 时是空白的。**

页面上的文字**一开始是透明的**，等程序跑起来才慢慢显示。如果程序加载失败，用户看到的是**一片空白**——不是"内容加载慢"，是"什么都没有"。

**③ 页面告诉浏览器"这是中文"，但产品是中英双语的。**

结果：用英文内容时，读屏软件会**用中文的发音去读英文**，听起来是乱的。**修它只要改一个词。**

---

### 2.5 简历页面上有个无限循环

这是这轮最应该马上修的一条，而且**根因已经找到，非常具体**：

打开任何一份公开简历（`/resume/xxx`），页面会**陷入无限循环**，反复重算，直到浏览器喊停。

- **触发范围比想象的广**：只要用户**不是**在这份简历的编辑模式里，就会触发——也就是说**每一位访客、每一位未登录用户都会遇到**。
- **根因**：有个负责"自动保存"的模块，在"当前不需要保存"时发了一个"停用"信号。问题在于，这个信号**每次都产生一个新的数据对象**，哪怕里面的内容一个字节都没变。而监听它的那段代码是"对象变了我就重新跑"——于是**永远在重新跑**。
- **最讽刺的地方**：那个文件**自己的注释里写着**"这个对象不能放进监听列表，放进去会死循环"。紧挨着的那段代码遵守了，**出问题的这段没遵守**。
- **它为什么能活到现在**：这个模块有 **51 个**测试、**全部通过**。但那些测试只测了"计算结果对不对"，而**计算结果确实是对的**。问题出在"结果被交给页面之后"——**没有任何一个测试看这一层**。

**我做了什么**：补了一条测试，专门盯住"内容没变时必须返回同一个对象"这条约定。这条测试**现在是失败的**（这正是它的作用——把缺陷变成可复现的证据），修好之后它会自动变绿，提醒把它改成正常测试。

**这条给我们的通用教训**（比修这一次更重要）：

> 任何"页面监听着它、它自己又会变化"的计算逻辑，都应该有一条测试，专门验证**"什么都没变的时候，返回的必须是同一个东西"**。

---

### 2.6 错误被当成"没有内容"显示给用户

这类问题比"页面崩溃"更伤信任，因为**用户不知道自己看到的是失败**：

| 位置 | 实际发生了什么 | 用户看到什么 |
|---|---|---|
| **"我的简历"页面** | 加载失败 | **"还没有简历"** —— 在自己的简历页上，这句读起来就是**"我的简历没了"**。**这条风险最高** |
| 公共简历列表 | 加载失败 | "暂无公共简历" |
| 登录状态检查 | 网络抖了一下 | **直接把用户登出**，还顺手删掉了登录凭证 |
| 简历页的权限检查 | 失败 | **编辑按钮不出现，页面上一个字都不解释** |

另外，**在站内点链接跳转时，没保存的修改会无声消失**（只有"关闭整个标签页"才会弹提示）。

## 三、值得做的新功能

下面**全部**是 44 个任务之外的，或者是对某个任务的具体补充。成本用日常单位标注：**小 ≈ 1–3 天 / 中 ≈ 1–2 周 / 大 ≈ 3 周以上**。

### 3.1 让 AI 助手更安全地帮人改简历

**① 让 AI 只改一个字段，而不是整份重传（中）**

现在如果有外部 AI 工具要帮忙改简历，它只能**把整份简历读走、改完再整份传回来**。风险很直接：**你在网页上手改的那一段，会被它覆盖掉**。

正确做法是：AI 只提交"把这一项从 A 改成 B"。系统只改这一处，**并且先检查改完的简历是否合法**——不合法就**一个字节都不改**，同时告诉它哪里错了。

**这条建议排在第一位，是因为它是后面几项的地基**，而且它**保护的是我们已有的防冲突机制**。

**② 告诉 AI"哪些能改、哪些不能"（小）**

给每个功能贴上标签：只是查看的 / 可以修改的 / 会造成破坏的（比如删除、改分享设置）。

另外，AI 读到的简历文字，要**明确标注"这是给你读的内容，不是给执行的命令"**。

**为什么这不是过度谨慎**：这是浏览器厂商自己发布的 AI 接口规范里**明确写出来的攻击方式**（"工具投毒"）。所以这是被规范要求出来的形状，不是我们多虑。

**③ 做几个"说明书"式的技能包（小）**

比如"按目标岗位定制""模拟面试""谈薪准备"。每个就是一份写好的说明书，用户在自己常用的 AI 工具里加载就能用。

**为什么性价比最高**：**主要是写文档，几乎不用写代码**，但能让我们出现在用户本来的工作流里——而且用的是**用户自己付钱的 AI**，我们零成本。

### 3.2 从"一份文档"变成"一条求职流水线"

**④ 定时帮你找岗位（大，建议先做一半）**

不是等用户来搜，而是系统**定期在后台找**，把结果放进一个"等你处理"的列表。

这里有个设计细节值得学：它要求"**网络搜索用一条连接，AI 用另一条，而且不配 AI 也能定时找**"。**好处是我们不必依赖 AI 的配额和计费体系**，可以先把找工作这部分做起来。

**建议先做一半**：先做"你贴链接、我排队查证"，再做自动抓取。

**⑤ 一次投递的完整工作区（中）**

从"我够不够格"到"表单怎么填"到"面试怎么聊"到"复盘"，放在一起。

**最值得先抄的是它的诚实设计**：会明确标出"**这一条主张目前没有证据支持**"，并把"有据可查的事实"和"只是我的观察"**分开放**。

**⑥ 每份简历配一个"私人备注"（小）**

记投给了谁、联系人是谁、这版改了什么。**不进简历正文。**

**关键**：必须**明确写清**它会不会出现在导出文件、公开页面里（答案是不能），并且**用测试钉死**，否则将来很容易不小心从导出功能漏出去。

**⑦ 删掉的简历能找回 + 改过名字后的旧链接还能用（小–大）**

现在删除是**真的删除**，找不回来。

- **"旧链接还能用"这一半成本很低，建议单独先做**：简历改过名字后，之前发出去的链接在 30 天内仍然能到达，并自动跳到新地址。
- **"回收站"那一半要小心**：不是加一个字段就完事，而是**所有"列出简历""查找简历""导出""分享""AI 写入"的地方都要认这个新状态**——漏掉任何一处，就等于没做，还会造成数据错乱。
- **为什么这半件必须先做**：用户最常见的一句抱怨就是"**链接发出去了，才发现简历要改**"。

**⑧ 让公开页面在手机上更好读（小–中）**

HR 在微信里点开链接是**高频场景**。现在页面在小屏幕上应该重排成**从上到下的可读文字流**，底部常驻下载和分享按钮。

另外链接**默认应该是关闭的**，可选"访客能不能下载 PDF"，**链接关掉或被删除时，访客只看到一句中性提示，不泄露任何信息**。

### 3.3 增长：一个不用登录就能用的"简历体检"

**⑨ 免登录、不上传的简历体检（中）**

用户上传简历 PDF，**全程在浏览器里完成，文件不上传、不存储**，立刻告诉他"招聘系统能不能读懂这份简历"。

**我们已经有全部零件**——判断文字层、分析规则、生成报告，都已经做好了，**只差把它们从"登录之后"搬到"登录之前"**。

**转化路径也很顺**：体检报告里说"这里有问题"，用户点"去修"，简历就在浏览器里等着，注册完直接导入。

**这一条撞上了一条我们自己的架构决定**（我们此前规定"不发布合成分数"），所以**需要你拍板**——见第五节。

### 3.4 信任：让"不编造"变成能查证的机制

**⑩ 一本"事实账本"（中）**

把用户真实的经历、数据**独立存成一份资产**，而不是每次都让 AI 从简历正文里重新猜。

每条事实标注来源（**用户自己说的，我们不假装核实过**）；用户更正后，**旧版本留痕，并自动提醒"哪些内容引用了它、需要重新检查"**；AI 记忆分三档（默认每次问 / 自动 / 绝不）。

**最值得注意的一条**：数据可以直接**留空**——**没有能支撑的数字，就不写数字**。

**为什么这条特别适合我们**：我们既有的原则就是"只给事实、每条能追溯到具体规则"。这一条**就是把这个原则从简历体检扩展到全部 AI 功能**。而且它还有个附带好处：AI 每次不用重读整份简历，**又省钱又稳定**。

**⑪ 让人在简历上行评论（中）**

在**具体的某一段**留评论、回复、标记已解决。

**为什么这个比"做导师平台"聪明**：国内简历修改服务通常是**双边市场**（要同时有足够多的用户和足够多的导师），很难冷启动。而做评论功能，**用户自带导师**——我们收获协作数据，但不用承担撮合责任。

## 四、明确不该做的事

这一节和上一节同样重要。下面每件事**技术上都能做到**，但**只有达到人家的规模才划算**——这类判断最容易被忽略，因为"做得到"看起来就等于"该做"。

| 不做 | 一句话原因 |
|---|---|
| **浏览器自动填表插件** | 用户是**精投少量岗位**，投递次数少 → 同样一份"适配各家招聘网站"的维护成本，**分摊到太少的使用次数上，这笔账算不过来**。而且出错的后果是**信任级事故**（悄悄填错、用户投出错误申请），不是普通 bug |
| **代投简历 / 批量投递** | 卖的是投递量，需要**招聘方的人脉网络**和**海量简历池**——两样我们都没有。而且它**主动放弃我们唯一的优势：准**。建议反过来讲："我们不替你投，我们让你投得更准" |
| **几万套模板** | 前提是巨大的搜索流量。上一轮已经确认过：**模板数量不是竞争点** |
| **导师辅导市场** | 双边市场（见 3.4 ⑪ 的替代方案） |
| **高校 B2B 就业系统** | **会改变公司形态**（招投标、私有化部署、按年结算），必须独立立项 |
| **薪酬数据平台** | 这是**数据生意**。连量级更大的国外同行都没有公开做出可信版本，说明要么成本极高、要么没有可行路径。**只做"用户自填区间"，并且逐项标明"未知"** |
| **"这段是不是 AI 写的"检测** | 找不到任何可复现的方法、基准或误报率数据。做它等于**给用户一个不可验证的判断**。**替代方案就是 3.4 ⑩ 的事实账本——提供可核查性，而不是猜测** |
| **在简历正文盖"AI 生成"的章** | 合规要求该做的是**导出文件的元数据**和**用户协议**；而在正文盖章**直接损害用户利益**（法规本身也允许用户申请不带标记的版本）。**"证明这是我本人写的"正确做法是来源标注 + 更正留痕**，不是猜哪句话像 AI |
| **把"导入领英"当卖点** | 那个导出包的信息量**比直接解析 PDF 还少**（后者我们已经做好了），数据在境外、流程繁琐，**对国内用户几乎零价值** |
| **花哨的图表、进度条、徽章模块** | 这类元素**正是招聘系统读不出内容的主要原因**（图标变空框、表格打乱阅读顺序），和我们的"高可读性"定位**直接冲突**。**应该反过来，把"不做这些"当卖点讲清楚** |
| **单独的"金句生成""自我介绍生成"入口** | 已经是红海，而且滑向"产出 AI 味内容"——**正是市场现在反感的方向** |

## 五、需要你拍板的两件事

### 第一件：要不要发布"合成分数"

背景：我们此前定过一条规矩——**体检报告只给事实，不给分数**，理由是分数很容易被当成"我的简历能得多少分"，而它其实衡量不了"你会不会被录用"。

但这轮我发现两件事：

1. **那条规矩自己前后不一致**：一边说"将来如果引入分数，必须满足三个条件"，另一边又说"发布合成分数"是被否决的方向。
2. **我们其实已经满足了其中最难的一条**：报告里每条问题都必须能追溯到具体规则、都带着证据。而且国外同行的公开体检工具**恰好就符合那三个条件**：分数完全由"文字能不能被读出来"这类可测量信号算出，"写作建议"**明确不计分**，页面上也**明说"这个分数反映的是能不能被软件读懂，不是你的录用概率"**。

三个选择：

1. **只给结论、不给数字**（比如"清爽 / 基本可读 / 软件难以读取"三档）——**完全不碰既有规矩，零风险**。
2. **公开版给分数、产品内保持只给事实**——需要**正式修改那条规矩**，并且改动测试里"禁止出现分数字段"的断言。
3. **维持现状**（不做体检）——代价是放弃这轮找到的**最强获客手段**。

**我的建议：先做第 1 种。** 成本和第 2 种差不多，风险为零，而且能先看真实用户会不会误读。第 2 种应该作为一次**正式的规矩修订**来提，而不是顺手放行——因为那条规矩的门槛是"**我们能为每一次分数波动逐条解释**"，这是一条**长期运营承诺**，不是一次性开发。

### 第二件：AI 内容标注怎么定性（建议走法务）

中国有两部法规已经生效，直接涉及"AI 生成的内容要不要标注"：

- 其中一条是**无条件的**：所有提供这类 AI 服务的，都要给生成的内容加**"不影响用户使用的标识"**，并在**文件元数据**里加信息。
- 另一条要求**显著标注**，但它有个前提条件——**"模拟真人"进行文字生成或编辑**。

**需要法务回答的就是这个前提**：「AI 辅助写简历」算不算"模拟真人"？
- 算 → 要触发"显著标注"义务，连**导出文件里也要带**。
- 不算 → 仍应完成元数据标识、服务协议说明等部分。

**但有两件事无论结论如何都该做，而且现在就能做**：

1. **查一下 AI 服务有没有把用户输入的完整内容（含姓名、电话）存进日志**——另一部法规**明确禁止**这么做。这是**当前就能查的工程问题**，不用等法务。
2. **补一份隐私说明和用户协议**——两部法规都要求告知，我们现在没有。

**另外提醒一句**：这跟"不做 AI 检测"不矛盾。**标注我们自己的产出是合规义务；猜测用户这段是不是 AI 写的，是不可验证的判断。** 前者要做，后者不做。

## 六、有些事我没能查证，如实说明

下面这些**我没有找到可靠依据，所以没有替它们下结论**（详情见技术版的第 8 节）：

- **欧洲的无障碍法规到底管不管我们**：它的适用主体是**州和地方政府**，对私有公司不直接适用；另一部欧洲法规**对微型企业有豁免**。真正决定的是**公司规模 + 是否向欧洲消费者销售**，不是服务器在哪。而且网上流传的那个合规截止日期**已经改了**（往后推了一年）。
- **招聘系统对 PDF 和 Word 有没有偏好**：**没有任何一家厂商的官方文档说过**。"必须用特定章节名""PDF 比 Word 更容易过筛选"这两句流传很广的话，**找不到依据**。
- **"给简历加结构化标记能提升搜索排名"**：找不到证据说明**有谁在消费这类标记**。所以相关任务的目标应该**限定为通用搜索优化**，不要宣称任何招聘系统收益。
- **数据出境**：网上说法普遍夸大了。按现行规定，**累计不满 10 万人、且不含敏感个人信息，是免申报的**。但**如果证件照被定性为敏感个人信息，结论会翻转**——这正好和我们要做的证件照功能相关，需要一起定性。
- **国外同行的具体功能细节**：有一家网站**全程拒绝访问**（返回 403），所以关于它的一切我都没有写。

**关于成本数字的说明**：报告里的代码体积数据是**解压后的体积，不是最终产物的体积**——因为你的开发服务器正在运行，跑正式打包有风险。同理，那两处数据库性能问题**机制已经确认，但没实测过具体慢多少**。

## 附：行话对照表

看技术版时可能遇到的词，这里一次性说清。

| 技术说法 | 日常说法 |
|---|---|
| **N+1 查询** | 本来一次能取回的东西，被**一份一份单独去取**了。一百份就是一百次往返 |
| **索引 / 缺失索引** | 书的**目录**。没有目录就只能从头翻到尾 |
| **数据库迁移** | 给数据库**升级结构**的那些记录（相当于"装修施工单"） |
| **渲染循环 / 无限渲染** | 页面**反复重算自己**，停不下来 |
| **重新渲染** | 页面重新算一遍该显示什么 |
| **reducer** | 一段"**根据收到的指令算出新状态**"的纯计算逻辑 |
| **依赖数组 / effect** | "**我盯着这些东西，它们一变我就重新跑一次**"的那份清单 |
| **引用相等（同一对象）** | 内容看起来一样，但**不是同一个东西**。计算机判断"变没变"看的是**是不是同一个**，不是"看起来像不像" |
| **乐观锁 / 版本冲突** | 两个人同时改同一份文件，系统**拒绝后改的那次**，避免悄悄覆盖别人的修改。靠的是每份文件有个**版本号** |
| **元数据** | 文件**自带的说明信息**（谁生成的、什么时候、用什么工具），不是文件正文 |
| **原子操作 / 全生效或全不生效** | **要么整件事都成功，要么当没发生过**，不允许"改了一半" |
| **opt-in / 显式同意** | 需要用户**主动勾选**，不能默认替他同意 |
| **硬删除** | **真的删掉**，找不回来 |
| **回归测试** | 专门用来**防止老问题重新出现**的测试 |
| **`it.fails`** | 一种写法：**这条测试现在必须是失败的**。它把"已知但没修的问题"变成**可运行、可复现的证据**；修好之后它会自动变红，提醒把它改成正常测试 |
| **可访问性 / 无障碍** | 让**用键盘、用读屏软件、看不清颜色**的人也能正常使用 |
| **读屏软件** | 把屏幕内容**念出来**的软件，视障用户的主要工具 |
| **behind a feature flag** | 先做出来但**藏在开关后面**，不默认给所有人用 |
| **上游 / 依赖** | 我们用的**别人写的代码库**。它升级或重构，可能让我们的代码失效 |
| **双轨 / 分环境** | 开发时一套行为，正式上线另一套（比如开发时打印详细信息，线上不打印） |
